# Wormhole、N300、T3K 与 Mesh 拓扑

## 文档契约

- owner：产品/逻辑 mesh、可见设备与通信拓扑。
- 依赖输入：`120` 的单芯片数据通路。
- 唯一输出：从 `MESH_DEVICE` 到 TT device mesh 的拓扑解释。
- 不讨论：scheduler lane 或模型容量；由 `124`、`126` 持有。

## 固定源码事实

插件 revision `f6995475739201fd1d2883adec477ecb37f951d9` 的 `src/vllm_tt_plugin/utils/dp_discovery.py::_NAMED_MESH_GRIDS` 将 `N300` 映射为 `(1, 2)`，将 `T3K` 映射为 `(1, 8)`。这是插件的逻辑 grid 解释，不应外推成任意机箱、主机或 PCIe 拓扑。

`parse_mesh_grid()` 接收命名 mesh 或显式 `(rows, cols)`；`_discover_standard_dp_visible_device_groups()` 再结合 `TT_VISIBLE_DEVICES` 和 data-parallel size 划分可见组。`TTWorker.init_device()` 消费解析后的设备选择，`TTCoreEngineLauncher` 传播 `MESH_DEVICE` 等环境变量。

## 三个不能混淆的编号域

| 编号域 | 含义 | owner |
|---|---|---|
| physical device/PCIe identity | 主机实际可枚举卡或 chip | driver/runtime |
| logical mesh coordinate | TTNN tensor distribution 与 collective 坐标 | TT runtime/model |
| vLLM rank/lane | 请求调度、worker 或 in-process lane | plugin/vLLM |

三者必须有可审计映射。仅看到 8 个 device 并不能证明它们组成 T3K 所需的 fabric；仅设置 `MESH_DEVICE=T3K` 也不能证明链路健康。

## 拓扑影响

模型权重和激活可以沿 mesh 做 tensor sharding、replication 或组合映射。collective 的关键不是抽象算法名称，而是消息是否沿物理邻接链路、是否跨 PCIe/host、是否需要 fabric 初始化，以及模型 kernel 的 shard spec 是否与 mesh shape 一致。

N300 的 `(1,2)` 与 T3K 的 `(1,8)` 使相同 logical tensor sharding 在参与者数、collective 消息数和失败域上不同。扩大 mesh 能容纳更大模型，却可能让 decode 每 token 的同步延迟变成主导项。

## 启动前验证顺序

1. runtime 可枚举预期 devices，标识不重复。
2. `TT_VISIBLE_DEVICES` 与逻辑 group 无重叠、无越界。
3. mesh open/close smoke test 成功。
4. 小型 P2P/collective correctness test 覆盖实际 group。
5. 模型声明支持该 mesh 和 shape。
6. 最后才运行 vLLM startup、正确性和性能测试。

## 故障语义

- 设备少于 grid：必须在初始化阶段 fail closed。
- 多个 DP group 复用同一 device：属于资源所有权错误，不能用重试掩盖。
- fabric 初始化成功但链路降级：启动 PASS 不等于通信性能 PASS。
- 进程退出未释放 device：下一次启动错误属于 lifecycle，不应误判为模型不支持。

## 证据分级

- `SOURCE_IMPLEMENTED`：上述 named-grid 和 group-discovery 逻辑。
- `VENDOR_CLAIM × UNVALIDATED`：150 的 `WEB-TT-01` 提供 Wormhole/TT software stack 的 mesh 与 fabric 概念；标签定义见 02。
- `INFERENCE`：更大 mesh 的 decode 同步风险。
- `UNKNOWN`：本机四张 N300 是否能作为一个受支持 mesh；没有实际枚举、fabric 和 release tuple 证据。
