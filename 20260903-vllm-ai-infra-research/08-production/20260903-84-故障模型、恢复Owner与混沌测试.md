# 故障模型、恢复 Owner 与混沌测试

## 文档契约

- **唯一问题**：每类故障由哪层检测、隔离、恢复和向用户定性。
- **In scope**：frontend/core/worker/device/network/storage故障，owner矩阵，retry/idempotency，chaos。
- **Out of scope**：安全攻击（85）、发布rollback（86）、connector细节（36）。
- **证据基线**：vLLM failure callbacks/process lifecycle及各子系统不变量。

| 故障 | 首检层 | 恢复owner | 默认影响域 |
|---|---|---|---|
| client disconnect | frontend | frontend/core abort | request |
| scheduler invariant | core | engine supervisor | engine |
| worker/RPC death | executor | replica supervisor | rank group |
| device async error/OOM | worker/executor | replica replacement | replica |
| collective hang | communicator/watchdog | cluster supervisor | group/node |
| artifact corruption | compiler loader | worker startup | revision/device |
| KV transfer partition | connector/router | P/D control plane | request/pool |

retry只有在side effects幂等、request version可识别且用户协议允许时安全。生成请求重试可能产生不同随机输出；HTTP层“未收到token”不证明core未执行。资源cleanup应exactly-once效果但允许重复调用。

故障恢复必须隔离可能部分写入的KV、runner buffers、artifacts和collective state。device reset后不要原地继续旧graph/handles。检测timeout需覆盖正常最长compile/forward/transfer，且避免无限等待。

chaos按线性化阶段注入：accept前后、scheduled/submitted/device-in-flight/output commit、transfer commit。检查无跨请求污染、无双输出、资源最终回收、SLO/error分类准确。一次“自动重启成功”不是完整韧性证据。

## Recovery epoch

恢复需区分 request attempt、engine/worker、process group、device context、artifact、KV lease epochs。小范围重试只有在更大范围状态可信时安全；device reset 后 graph/queue/buffer、communicator fault 后 group 通常不可继承。

混沌 artifact 保存 trigger、注入时刻、detector、decision、cleanup、replacement readiness 与客户端结果。`SOURCE_IMPLEMENTED`：process/future/abort hooks；`RECOMMENDATION`：按线性化点注入；`UNKNOWN`：vendor cancel/reset保证。
