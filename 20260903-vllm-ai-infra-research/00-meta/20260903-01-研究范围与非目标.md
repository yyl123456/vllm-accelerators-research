# 研究范围与非目标

## 本篇唯一主问题

本文档集对“vLLM 与异构 AI 推理基础设施”做出什么级别的回答，又有哪些结论明确不在授权和证据范围内？

## In scope

- vLLM V1 的请求、调度、KV、执行、模型、编译、采样、通信、插件和 serving 路径。
- Ascend、Qualcomm Cloud AI 100/80、Tenstorrent Wormhole/N300/T3K、Google TPU 的公开硬件机制与 vLLM plugin/runtime 映射。
- 架构决策：状态 ownership、抽象边界、版本 tuple、故障域、可观测性、性能实验和生产门禁。
- 固定 revision 下的源码事实、公开 release contract、厂商资料、可证伪推断和未知项。

## Out of scope

### 不做产品支持背书

本研究没有在 Ascend、Cloud AI、Tenstorrent 或 TPU 设备上执行模型，因此不能宣布：

- 任何模型/量化/上下文/并发/并行组合已数值正确；
- 任何多卡或多主机 topology 已通信稳定；
- abort、OOM、collective timeout、device reset 或 worker crash 已安全恢复；
- 任何厂商在未指定 workload 时比另一厂商更快、更省或更可靠。

### 不代替安装和运维手册

文档会解释 release tuple 为什么重要，但不保证提供某一天可直接复制的安装命令。安装手册容易因 driver、firmware、container tag 和 package index 改变，应由目标 release 的官方资料所有。

### 不遍历所有生态 Backend

深度对象只有四个：Ascend、QAIC、Tenstorrent、TPU。CUDA、ROCm、CPU、XPU、Gaudi 可作为 upstream 契约或对照证据，但不享有同等的 vendor 章深度。

### 不推导非公开硬件实现

公开资料未说明的 on-chip network arbitration、cache coherence、compiler cost model、firmware scheduler 或 error recovery 机制不会由类比补齐。相应问题保留为 `UNKNOWN`。

## 时间边界

- 基线日期：2026-09-03，Asia/Shanghai。
- branch 名称如 `main`、`dev` 只是抓取来源；文档事实绑定 commit SHA。
- 文档引用“当前”时，默认指上表 revision，不指未来 branch HEAD。
- 任何随时可变的支持表、容器 tag、SDK 版本和产品规格必须附访问日期。

## 授权边界

本轮可以：

- 读取本地仓库和公开网络资料；
- 把必要的公开仓库浅克隆到 Temporary/Scratch；
- 在 Temporary/Documents 写中文文档；
- 做静态源码分析和无设备的主机检查。

本轮不可以：

- 修改任何项目源码或项目版本控制文件；
- 创建 branch/commit，push，或创建 PR/MR/issue；
- 下载模型权重、大型容器或受限 SDK；
- 使用凭据、付费计算资源或未授权真实硬件。

## 要回答的架构问题

本研究的最终消费者应能用它回答：

1. 一个请求从 API 进入到 token 流输出，每个状态由谁所有？
2. scheduler 与 device runner 之间交换什么，哪些假设对非 GPU 后端造成约束？
3. 逻辑 KV block、物理 KV tensor、prefix cache 和 remote/offload 状态如何协作？
4. 不同编译/图/trace 模式如何与动态 serving 请求对接？
5. TP/PP/DP/EP/context parallelism 如何映射到通信、拓扑和故障域？
6. 一个 vendor plugin 究竟复用了 vLLM 的什么，又重写了什么？
7. 在什么证据下可以称为“可安装”、“功能支持”、“生产可用”或“性能达标”？
8. 当一个新硬件接入 vLLM 时，关键决策、高风险边界和验证顺序是什么？
