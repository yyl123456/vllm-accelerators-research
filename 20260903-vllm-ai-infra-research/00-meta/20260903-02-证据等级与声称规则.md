# 证据等级与声称规则

## 本篇唯一主问题

对 vLLM 和硬件 backend 的一条陈述，需要什么证据才能被写成事实、支持、验证或性能结论？

## In scope

证据类型、claim 原子性、来源强度、版本时效性、反证、降级规则和审查门禁。

## Out of scope

不在本篇列出所有引用 URL，不解释某个 backend 的实现，不评定具体性能。

## 两个正交维度

每条 claim 必须分别填写“事实来源类型”和“验证成熟度”，不得把两者压成一个含混标签。前者回答“谁/什么载体作出陈述”，后者回答“我们实际证明到哪一步”。例如，厂商规格页只能形成 `VENDOR_CLAIM × UNVALIDATED`；固定源码中的可达路径是 `SOURCE_IMPLEMENTED × STATIC_REVIEWED`；指定设备上的数值测试才可能是 `EXPERIMENT_RESULT × DEVICE_NUMERIC`。

### 事实来源类型

| 标签 | 含义 |
|---|---|
| `SOURCE_IMPLEMENTED` | 固定 revision 中存在可达实现；必须给 repo/SHA/符号/caller |
| `RELEASE_CONTRACT` | 明确 release/tag/image/ModelSpec/兼容矩阵作出的交付承诺 |
| `VENDOR_CLAIM` | 厂商公开材料或 datasheet 的陈述，尚未被本研究独立验证 |
| `EXPERIMENT_RESULT` | 有命令、环境 tuple、日志、输出和验收条件的本研究或引用实验结果 |
| `INFERENCE` | 从已知前提推导、可被反例推翻的分析 |
| `RECOMMENDATION` | 在给定目标和约束下提出的设计选择 |
| `UNKNOWN` | 缺少形成事实结论所需的证据 |

### 验证成熟度

| 标签 | 最低证据 | 可证明范围 |
|---|---|---|
| `UNVALIDATED` | 只有文档/声称，或尚未检查可达性 | 不证明安装、运行或正确性 |
| `STATIC_REVIEWED` | 固定源码、符号、caller、guard、版本均已审阅 | 只证明静态可达实现 |
| `HOST_VALIDATED` | 无目标设备的 import/config/unit 测试及日志 | 只证明 host/control path |
| `DEVICE_SMOKE` | 固定 tuple 上启动、加载、最小执行、清理 | 只证明该最小路径可运行 |
| `DEVICE_NUMERIC` | 明确输入/golden/tolerance 的设备数值测试 | 只证明指定 workload 的数值正确 |
| `STRESS_VALIDATED` | 并发、长时、取消、故障注入及资源回收 | 只证明覆盖的压力/故障域 |
| `PERFORMANCE_MEASURED` | 完整 workload/tuple/topology/raw data | 只证明该实验域内的性能 |
| `PRODUCTION_QUALIFIED` | release contract、回归矩阵、SLO、回滚和运维证据 | 只证明声明的生产支持域 |

### 旧标签映射（禁止在新正文继续使用）

| 旧写法 | 规范写法 |
|---|---|
| `AUTHORITATIVE`、`VENDOR_DOCUMENTED` | 若来自厂商网页：`VENDOR_CLAIM × UNVALIDATED`；若来自明确版本支持矩阵：`RELEASE_CONTRACT × UNVALIDATED` |
| `SOURCE_ONLY`、`SOURCE` | `SOURCE_IMPLEMENTED × STATIC_REVIEWED` |
| `HOST` | 对应来源类型 `× HOST_VALIDATED` |
| `DEVICE`、`DEVICE_SMOKE` | 对应来源类型 `× DEVICE_SMOKE` |
| `NUMERIC`、`NUMERIC_VALIDATED`、`DEVICE_CORRECT`、`DEVICE_NUMERIC` | 对应来源类型 `× DEVICE_NUMERIC` |
| `STRESS`、`STRESS_VALIDATED` | 对应来源类型 `× STRESS_VALIDATED` |
| `PERF`、`PERF_VALIDATED`、`PERFORMANCE_VALIDATED` | 对应来源类型 `× PERFORMANCE_MEASURED` |
| `RELEASE`、`PRODUCTION` | `RELEASE_CONTRACT × PRODUCTION_QUALIFIED`；没有生产门禁时不得使用 |

后文“证据等级”是来源类型的详细声称规则；成熟度必须另列，不能把 `VENDOR_CLAIM` 与 `DEVICE_NUMERIC` 当作同一轴上的强弱等级。

## 来源类型的详细声称规则

| 标签 | 它证明什么 | 它不证明什么 | 最小证据 |
|---|---|---|---|
| `SOURCE_IMPLEMENTED` | 固定 revision 存在可达实现 | 实机正确、发布支持、性能 | repo、SHA、文件/符号、可达路径 |
| `RELEASE_CONTRACT` | 某个 release 对 tuple/功能作出明确承诺 | 本地环境已安装或运行 | release/tag/image/ModelSpec/版本矩阵 |
| `EXPERIMENT_RESULT` | 固定 tuple 与 workload 有可复现实验 | 其他模型、shape、topology、故障路径 | 命令、环境、日志、输出和 acceptance；成熟度另列 |
| `VENDOR_CLAIM` | 厂商公开材料如此陈述 | 独立验证或对 vLLM 的实际效果 | 厂商原页、访问日期、语境 |
| `INFERENCE` | 由已知事实导出的可证伪判断 | 已实现或已验证 | 前提、推理链、反例条件 |
| `RECOMMENDATION` | 在给定目标/约束下的架构选择 | 项目当前行为 | 决策驱动、备选项、trade-off |
| `UNKNOWN` | 当前证据不足 | 不支持或永远不可能 | 缺失证据与可消除它的实验 |

## Claim 必须原子化

错误声称：

> Backend X 支持 Model Y。

该句同时隐含了可发现、可加载、可编译、可执行、数值正确、API 完整、多请求安全、特性组合可用和生产可维护。它必须拆成：

1. registry 能将 Model Y config 解析到某个 class；
2. loader 能在指定 dtype/quant/layout 下加载权重；
3. runner 能为指定 device/SKU/topology 构造 executable/program；
4. 指定 prompt/decode shape 可执行；
5. 输出通过明确的数值验收；
6. 所需的 streaming、logprob、LoRA、grammar、prefix cache、parallelism 组合通过；
7. 存在可复现 release tuple 和运维边界。

每条可以拥有不同证据等级，不能取其最强者代表整体。

## 来源强度和优先级

在同一 claim 上，默认优先级是：

1. 当前固定 revision 中的可达源码和测试产物；
2. 同 revision/tag 的官方 release note、support matrix 和 API 文档；
3. 硬件/软件厂商官方文档；
4. 原始论文和项目设计文档；
5. issue/PR/discussion 中与具体 revision 关联的维护者说明；
6. 二手博客、汇总页或搜索摘要。

优先级不代表绝对正确。例如注释可能落后于实现，release matrix 可能只覆盖单项而非组合。发生矛盾时，记录双方 revision 和可观测行为，不用“通常”消解矛盾。

## 可达性规则

找到 class/function/file 不自动获得 `SOURCE_IMPLEMENTED`。还需要证明：

- 它由 entry point、factory、registry 或当前 config 选择；
- 没有被恒为 false 的 guard、dead branch 或旧 V0 路径隔离；
- 它的 caller 传入了该 claim 需要的数据；
- 如果是 patch/monkey patch，import 顺序能使它在目标进程生效；
- 如果是 backend selector，所需 package/device capability 条件成立。

对于没有目标 runtime 的本次研究，可达性通常只能证明静态 control-flow，不能证明 binary kernel 或 compiler 最终成功。

## 版本 tuple 规则

异构 backend 的兼容单元不是一个 Python package 版本，而是至少：

```text
vLLM commit/tag
+ plugin commit/tag
+ model implementation revision
+ framework/runtime/compiler
+ custom-op ABI
+ driver
+ firmware
+ hardware SKU/topology
+ model revision/tokenizer
+ dtype/quantization
+ container/OS/Python
```

若某项不适用，必须显式写 `N/A` 和理由，不能留空后仍宣称 tuple 完整。

## 组合支持规则

若支持表分别写了 FP8、LoRA、prefix cache 和 TP，不能推导 `FP8 + LoRA + prefix cache + TP` 可用。组合 claim 至少需要：

- 显式组合矩阵；或
- 该组合的可达测试和通过产物；或
- 设计上证明功能状态和数据面互不影响，并有最小 runtime 验证。

第三种条件在复杂推理系统中很少能完全满足，因为功能常在 batch layout、KV、RNG、graph capture 和 communication buffer 上相遇。

## 性能声称规则

一条可比性能 claim 必须同时指定：

- model/tokenizer revision、dtype/quantization、权重布局；
- prompt/output length 的分布，而非只是均值；
- request arrival model、concurrency、batch/admission 参数；
- TTFT、TPOT/ITL、throughput、error rate 中实际测量的指标；
- warm/cold cache、compile/graph/trace warmup 是否计入；
- SKU 数量、topology、clock/power mode、driver/firmware/runtime tuple；
- 重复次数、分位数、异常值处理和原始记录。

缺任一关键维度时，数字只能被称为 `VENDOR_CLAIM × UNVALIDATED`，或局部 `EXPERIMENT_RESULT × PERFORMANCE_MEASURED`，不能用于普遍排名。

## 降级规则

- 只有源码，没有目标 runtime：只能写 `SOURCE_IMPLEMENTED × STATIC_REVIEWED`，不能写 `EXPERIMENT_RESULT × DEVICE_SMOKE` 或更高成熟度。
- 只有 README 宣称，无 release artifact/matrix：降为 `VENDOR_CLAIM` 或项目声称。
- 本地测试与文档不同 revision：不能直接为当前 revision 背书。
- 单卡测试外推多卡：降为 `INFERENCE`，通信正确性为 `UNKNOWN`。
- 功能单测外推组合：组合结论为 `UNKNOWN`。
- 理论 FLOPS/带宽外推 tokens/s：只能作瓶颈分析的输入，不是性能证据。
- Future/event 存在外推真实 device completion：保留 `UNKNOWN`，直到证明后端 completion contract。

## 审查门禁

任一以下情况是 P0：

- 把设计意图或建议写成当前行为；
- 把 source existence 写成 end-to-end support；
- 把硬件规格写成服务性能；
- 把单项 feature 写成任意组合支持；
- 把未验证的取消、抢占、故障和完成语义写成安全；
- 不指定 revision 却使用“当前源码”作为证据。

## 本篇输出契约

所有其他文档只引用这套标签和规则，不重复定义。一条 claim 的 owner 文档必须提供证据或显式标为 `UNKNOWN`。
