# 术语表与状态 Owner 索引

## 本篇唯一主问题

文档集中重复出现的术语分别指什么，一类运行时状态的语义 authority 在哪个层次？

## In scope

简明术语、状态副本、authority/owner、产生者、消费者、同步边界和对应专题文档。

## Out of scope

本篇是索引，不展开调度算法、KV 结构、runner 实现或 vendor 映射。“owner”也不意味着其他层没有缓存副本。

## Owner 的定义

本文档中的 owner 是指：对某个状态转移有最终语义决定权，并必须维护其不变式的组件。其他层可以持有：

- **projection**：为下游执行投影出的子集；
- **cache**：可从 authority 重建的性能副本；
- **reservation**：尚未提交的资源保留；
- **observation**：不能反向修改 authority 的 metrics/trace 快照；
- **physical realization**：把逻辑状态映射为 device buffer/program 的表示。

如果两个组件都能无协议地修改同一语义状态，这不是“共同 owner”，而是需要修复的 split-brain 风险。

## 关键术语

### 请求与调度

- **request**：拥有 request ID、输入、采样/池化参数和生命周期的服务单元。
- **iteration/step**：scheduler 产生一次执行计划并处理返回的控制周期；它不必等于一个 kernel 或一个 token。
- **continuous batching**：在 iteration 边界重组活动请求，不等于所有 backend 都能在同一 device batch 混合 prefill/decode。
- **admission**：决定请求或部分 token work 能否进入当前资源窗口。
- **preemption**：暂停已运行请求并回收/保留部分状态以便日后恢复；不是 abort 的同义词。
- **abort**：客户端或系统要求请求终止，必须处理已排队、已提交和已输出状态。

### KV 与内存

- **KV cache**：attention 为已计算 token 保留的 key/value 状态；hybrid/Mamba 模型还可有非 KV recurrent state。
- **logical block**：scheduler 用于分配、共享和回收的抽象单元。
- **physical layout**：block 在具体 tensor/buffer/device/rank 上的 shape、stride、dtype 和位置。
- **prefix cache**：通过内容身份复用已计算前缀的机制；命中 block 不代表所有 token 都免于重算。
- **offload**：将状态从主执行设备移到 CPU/磁盘/远程层，不等于 P/D 解耦。
- **KV transfer**：在 producer/consumer 间传递 KV 及其 metadata 的协议。

### 执行和编译

- **executor**：将 engine 调用 fan-out 到本地 worker、子进程或 Ray actor 的拓扑/运输层。
- **worker**：管理某 rank 的 device、model runner、memory profile 和分布式上下文。
- **model runner**：把 `SchedulerOutput` 变成 batch/device inputs，执行模型与采样，并产生 model-runner output。
- **attention backend**：attention metadata、KV layout 要求和 kernel/implementation 的组合契约，不只是一个 kernel 名称。
- **eager**：按 runtime/operator 调用即时执行；它仍可以使用预编译 kernel。
- **JIT compile**：在部署或请求期间根据 graph/shape 产生 executable。
- **AoT compile**：在服务运行前产生受 model/shape/SKU/SDK 等约束的 artifact。
- **capture/replay**：捕获已确定的执行序列并以更低 host overhead 重放；不自动等于 compiler 优化。
- **completion**：一个操作对其 consumer 可安全观测的时刻；host submit、queue accepted、device executed、D2H visible 是不同边界。

### 并行和拓扑

- **TP**：将一层内的 tensor/operator 工作分到多 rank。
- **PP**：按模型层或 stage 分割，通过 microbatch/activation 传递重叠阶段。
- **DP**：复制模型服务能力并在 replica/rank 间分配请求；路由可在 engine 外部。
- **EP**：将 MoE expert 分布到 rank，通常需要 all-to-all/token dispatch。
- **context parallelism**：沿 sequence/context 维度分割 attention/KV 工作；本文会分开 DCP 与 PCP 的具体语义。
- **logical device ID**：framework/scheduler 使用的编号；它不必是 OS 枚举的单个物理设备。
- **topology**：设备、链路、主机、NUMA 和 failure domain 的关系，不只是 device count。

## 状态转移的通用不变式

1. **单一 authority**：每个语义状态必须有一个最终裁决者。
2. **单调提交**：已向客户端公布的 token 不得因 preemption/retry 改写。
3. **使用前可见**：下游使用 KV/output 前，产生它的 device work 必须达到正确 completion 边界。
4. **回收后不可写**：物理 block/input slot 被重用前，不得有旧请求的 in-flight writer。
5. **恢复不重放已提交输出**：preemption/retry 必须区分已计算、已接受、已公布和 stale output。
6. **副本可证明一致**：runner/frontend/connector 的 cache 必须有 version/sequence 或重建规则。
7. **观测不改变语义**：metrics/tracing 不得成为 correctness 所需的唯一状态通道。

## 源码锚点

- `vllm/v1/engine/__init__.py`：`EngineCoreRequest`、`EngineCoreOutput`。
- `vllm/v1/engine/output_processor.py`：frontend `RequestState`。
- `vllm/v1/request.py`：core `Request`、in-flight/stale/placeholder/sequence 状态。
- `vllm/v1/core/sched/scheduler.py`：waiting/running、schedule/update/free。
- `vllm/v1/core/sched/output.py`：scheduler 到 runner 的投影数据。
- `vllm/v1/core/kv_cache_manager.py`、`kv_cache_coordinator.py`：逻辑 KV 生命周期。
- `vllm/v1/worker/gpu/model_runner.py`：runner request/input/model/sampling 副本。
- `vllm/v1/executor/abstract.py`：executor 调用与 async 返回面。

这些路径证明当前源码中存在多层 request state，但具体不变式是源码分析的归纳；若缺少对应 runtime/fault test，不得标为 `EXPERIMENT_RESULT × DEVICE_SMOKE + STRESS_VALIDATED`。
