当前权威集合精确为 105 篇；逐组文件清单和数量以根目录的 [执行计划](../20260903-架构研究文档重构执行计划.md) 为唯一 manifest。本篇只提供阅读路径，不重复列举文件。

## 本篇唯一主问题

读者应如何按自己的架构任务，在不重复阅读的前提下组合本文档集？

## In scope

文档分层、依赖方向、阅读路线、单篇输入/输出契约和跨篇引用规则。

## Out of scope

不在本篇解释 vLLM 源码、硬件细节、性能数字或 vendor 支持结论。这些内容只存在于对应 owner 文档。

```text
  ↓

  ↓

  ↓

  ↓

```

箭头表示语义依赖，不表示读者必须线性阅读全部内容。

## 四条阅读路线

### 路线 A：vLLM 源码架构师

1. 证据规则和状态 owner 索引；
2. `02-vllm-control`：请求如何进入、排队、执行和完成；
3. `03-vllm-kv-memory`：逻辑 block 与物理 tensor 如何分工；
4. `04-vllm-execution`和 `05-vllm-compile`：batch 如何变成 device work；
5. `06-vllm-distributed`：单 engine 语义如何拓展到多 rank；
6. `07-platform-plugin`：哪些是后端合法扩展点。

这条路线的输出是一张可用于 code review 的 owner/invariant/call-chain 地图。

### 路线 B：AI Infra 和生产架构师

1. `01-ai-infra`：workload、SLO、admission、多租户与成本模型；
2. `08-production`：API backpressure、metrics、benchmark、capacity、failure、security、upgrade；
3. `06-vllm-distributed`：部署拓扑对通信和故障域的影响；
4. `14-decisions`：将业务限制转换为选型和上线门禁。

这条路线不要跳过 SLO 和 benchmark 定义直接阅读 vendor 规格，否则容易把理论带宽误写为服务吞吐。

### 路线 C：新硬件 Backend 负责人

1. `09-hardware-foundations`：先建立硬件语言；
2. `07-platform-plugin`：确定 upstream 扩展面和内部 API 漂移面；
3. `02`–`06` 中与目标后端有关的状态、KV、runner、compile、parallelism 契约；
4. 任选两个 vendor 章作为对照，不把单一 vendor 方式视为模板；
5. `14-decisions/143`：分阶段接入方法。

这条路线的输出是支持域、版本 tuple、实现边界和验证矩阵，不是“能 import plugin”。

### 路线 D：硬件选型与技术尽调

1. `01-ai-infra/11`、`12`、`16`：确定 workload、SLO 和瓶颈模型；
2. `09-hardware-foundations`：使用相同的计算/存储/互联/completion 维度；
3. `10`–`13`：各 vendor 的硬件、runtime、plugin、release 和验证边界；
4. `14-decisions/141`、`142`、`144`：功能证据、成本风险和生产决策。

若不能给出模型、精度、上下文、并发、输入/输出分布、拓扑和版本，就不能从该路线得出性能结论。

## 跨篇引用规则

- 一个概念只有一篇 owner 文档负责定义、内部机制和边界。
- consumer 文档只能写“使用哪个契约、本 backend 如何映射、有何差异”，并链接 owner。
- 不在每个 vendor 章重写 prefill/decode、PagedAttention、roofline 或 evidence level。
- 比较文档只消费各 owner 的结论，不引入新事实。
- 一个结论如果需要两个 owner，拆成“机制事实”与“架构影响”两条 claim，通过 ID 关联。

## 阅读时如何识别结论强度

正文中的事实声称使用证据等级，具体含义由 [证据等级与声称规则](./20260903-02-证据等级与声称规则.md) 唯一定义。阅读者应把 `SOURCE_IMPLEMENTED` 解读为“找到固定 revision 的可达实现”，而不是“已在目标硬件上正确运行”。
