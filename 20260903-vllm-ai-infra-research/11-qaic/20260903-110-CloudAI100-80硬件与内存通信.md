# Cloud AI 100/80 硬件与内存通信

## 文档契约

- **唯一问题/Owner**：Qualcomm Cloud AI accelerator 作为 PCIe inference device 的资源/通道模型如何约束 serving。
- **依赖输入**：90-95硬件比较语言。
- **唯一输出**：供111-116使用的device/DRAM/PCIe/channel/多设备约束。
- **Out of scope**：SDK与QPC（111）、plugin（112-116）、未经官方tuple核验的峰值。
- **权威来源**：[Cloud AI SDK 安装检查](https://quic.github.io/cloud-ai-sdk-pages/1.19.8/Getting-Started/Installation/Checklist/checklist/index.html)、[qaic-util](https://quic.github.io/cloud-ai-sdk-pages/1.21/Getting-Started/SDK-Tools/shared/qaic_util.html)、Qualcomm产品资料。

Cloud AI device经PCIe暴露给Linux，QID与PCI SBDF都是设备identity视图。官方checklist要求PCIe enumeration、MHI device nodes和`qaic-util` Ready状态；这三层分别验证host枚举、driver channels与SoC boot，不能互相替代。

`qaic-util`可查询firmware、DRAM、network status、physical channels、ECC和multi-device partitioning。physical channels是host/device数据传输与activation资源，不等于vLLM request并发；需要由runtime activation/profile映射。

多device P2P/MDP受PCI hierarchy约束，官方文档要求相关devices位于同一PCI switch下的连续层次并检查P2P+/MDP+。因此逻辑QID列表不能证明peer path；跨socket/ACS设置会改变effective bandwidth与failure domain。

硬件面向低功耗推理并有多个SKU/代际；fixed plugin setup中还按Hexagon ISA区分V68 AI100与V81+ AI200的BF16 kernel build，说明指令/dtype能力不能跨代外推。文档标题沿项目命名保留100/80，但所有支持结论须绑定实际SKU。

`UNKNOWN`：本轮无设备，DRAM容量、sustained BW、NSP/activation映射和多卡LLM性能不作声称。设备验收保存QID↔SBDF↔NUMA/PCI tree、firmware/DRAM/ECC/channels及P2P状态。

## 地址空间与容量问题

部署必须分别回答 weights、KV、activation、QPC/session buffers 与 host staging 位于 device DRAM 还是 host memory，以及是否按 physical channel/partition 复制。总 DRAM 减法只有在 runtime 能报告 reservation/fragmentation 时才可信。

| identity | owner | 验证 |
|---|---|---|
| QID↔SBDF | driver/qaic-util | 枚举与重启稳定性 |
| SBDF↔NUMA/root | OS/PCI topology | placement |
| QID↔session/channel | SDK/plugin | submit/metrics/fault |

`VENDOR_CLAIM × UNVALIDATED`：150 的 `WEB-QAIC-01/04` 记录枚举/MHI/Ready/P2P 工具；`INFERENCE`：QID mapping 必须贯穿 worker/metrics；`UNKNOWN`：本机物理映射与容量。标签定义见 02。
