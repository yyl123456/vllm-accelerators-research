# QAIC Eager 执行、KV 与特性边界

## 文档契约

- **唯一问题/Owner**：Pyt/eager路径如何逐step执行动态vLLM batch与paged KV。
- **依赖输入**：42-49 runner contracts；112 mode selection。
- **唯一输出**：Pyt runner/attention/custom-op/KV mapping及边界。
- **Out of scope**：QPC/AoT（114）、全局调度/sampling矩阵（115）。
- **源码基线**：vllm-qaic `3212cc...` 的 `QaicWorkerPyt`、`QaicModelRunnerPyt`、QAic attention与csrc ops。

Pyt runner继承GPUModelRunner contract，使用QAIC device/tensors与custom ops。attention backend有normal/full-block variants，C++/Hexagon kernels包含reshape-and-cache、RMSNorm、router等。这是一条动态runtime路径，不等同于CPU eager。

paged KV要求core block IDs、QAIC block table、device reshape/cache store/load和attention读取一致。full-block backend名称提示某些kernel对完整blocks有不同假设；partial page、prefix最后token、preempt/reuse必须专项测试。

memory profiling需扣除runtime/QPC-less graph、weights、temporary和KV；PCIe/physical channels会影响H2D/output。device async output classes存在，意味着Future/output retirement与buffer reuse需映射实际completion。

BF16/quant/custom kernels受AI100/AI200 ISA和build artifact影响；源码存在op不保证当前wheel包含目标variant。MM、LoRA、spec、P/D示例/模块存在，也必须通过49B组合矩阵。

验证从custom-op reference、attention/page canary、single request greedy到batch churn/preempt/prefix，再扩展features与多device。`SOURCE_IMPLEMENTED`证明路径；无QAIC设备时numeric/completion/perf为`UNKNOWN`。

## 固定源码链

`worker/worker.py::QaicWorkerPyt` 构造 `worker/model_runner.py::QaicModelRunnerPyt(GPUModelRunner)`；attention 使用 `attention/backends/qaic_attn.py` 或 `qaic_attn_fullblocks.py` 的 metadata builder/impl；`_custom_ops.py` 与 `ops/` 提供 dispatch。

继承 GPU runner 时需扫描未 override 的 CUDA stream/allocator/graph assumptions；class inheritance 不是语义证明。logical block ID→QAIC metadata→reshape/cache op→attention read 必须与 completion 同 epoch。

`RECOMMENDATION`：建立父类 reachable-call diff 和 block reuse delayed-completion test；`UNKNOWN`：实际 PrivateUse/device tensor 与 async memory visibility。
