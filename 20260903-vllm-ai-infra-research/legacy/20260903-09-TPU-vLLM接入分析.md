# TPU vLLM 接入分析

## 核心结论

当前 TPU 路径由 `vllm-project/tpu-inference` 承担。它是 OOT hardware plugin，同时提供 JAX 与 PyTorch/TorchAX 模型路径、自有 TPUModelRunner、XLA runtime、SPMD sharding、Pathways 和 TPU-specific connector。它复用 vLLM 服务与调度协议，但执行平面不是 CUDA-style eager kernel 的简单移植。

## 软件与执行栈

```text
vLLM API / EngineCore / SchedulerOutput
        ↓
tpu-inference Platform / Worker / TPUModelRunner
        ↓
JAX model 或 PyTorch→TorchAX
        ↓
XLA / PJRT / libtpu / optional Raiden / Pathways
        ↓
SPMD sharding + ICI collective
        ↓
TPU MXU / vector / scalar / HBM
```

仓库称其为 unified JAX/PyTorch plugin，但“统一”主要指共同的 TPU execution/lowering 目标；源码仍有 JAX 与 vLLM-compatible model loader、权重和模型实现分支。不能写成所有中间表示与 cache 完全共用。

## 硬件架构

Google 官方文档说明 TPU TensorCore 由 systolic MXU、vector unit 和 scalar unit组成。v6e 每 chip 32GB HBM、1638GB/s HBM bandwidth、800GB/s 双向 ICI，并采用最多 256 chips 的 2D torus；8-chip single-host 配置专门面向 inference。[TPU architecture](https://docs.cloud.google.com/tpu/docs/system-architecture-tpu-vm)；[TPU v6e](https://docs.cloud.google.com/tpu/docs/v6e)

矩阵单元适合大 GEMM；softmax、normalization、sampling 和地址操作落到 vector/scalar。高效 serving 需要让 batch/sequence shape、SPMD sharding 和 ICI collective 同时匹配。

## Platform 与 runtime 生命周期

`SOURCE_IMPLEMENTED`：`TpuPlatform` 使用 XLA dispatch、`TPU_VISIBLE_CHIPS`、自有 communicator/worker 和 attention backend；可选择 uni、multiprocess 或 Ray executor。它禁用普通 torch.compile，交给 TorchAX/JAX/XLA。

plugin 在 import 早期加载可选 Raiden XLA runtime，以避免它与 jaxlib 的另一份 XLA 在 static initializer 冲突；Pathways 路径还需在其他 JAX 操作前初始化并提前解析 `current_platform`。

`INFERENCE`：runtime 生命周期超出了普通 Engine 对象，部署上应优先采用进程隔离；热重启、同进程多 Engine 和 fork-after-runtime-init 需要专项测试。

## Shape 和编译

XLA 的收益来自跨算子 lowering、静态内存规划和 SPMD，但动态 continuous batching 会产生多个 shape。常见策略是 padding/bucket、预编译/预热以及将 decode 维持在少数稳定 shape。

架构风险：

- compile cache miss 抬高 TTFT；
- bucket 太少造成 padding 和无效 MXU 工作；
- bucket 太多增加编译、cache 和 warmup 成本；
- topology 或 sharding 变化会使 artifact 失效；
- host callback/D2H sampling 可破坏流水。

## 模型与 KV

自定义 JAX model contract 要求 `vllm_config`、mesh、KV arrays、input IDs 和 attention metadata，并需单独实现权重加载和注册。PyTorch 模型通过兼容 wrapper/TorchAX 进入 TPU execution。

TPU runner 管理 KV、input state 和 sampling，并有 connector/offload 扩展。`TpuPlatform.mem_get_info()` 聚合本地 devices 的 HBM stats，以匹配 global tensor 维度的容量推导。

`UNKNOWN`：JAX 与 PyTorch 路径是否对所有模型共享完全相同的 KV representation、cache key 和 failure semantics；本次只确认共同平台目标和并存实现。

## 并行

TPU 的自然抽象是 mesh/SPMD。单 host、multi-host、Pathways、attention DP、vLLM multiprocess DP 并非任意组合；源码会根据配置选择单进程 SPMD 或不同 executor，并拒绝部分冲突。

拓扑是编译输入：相同模型换 chip count 或 mesh shape，通常需要重新 sharding、编译和调优。ICI 内的 slice 与跨 DCN/multislice 也不是同一性能域。

## 主要风险

- XLA/JAX/PyTorch runtime 版本和加载顺序；
- compile/sharding cache provenance；
- 动态 batch 与静态 shape 的冲突；
- Pathways/multiprocess/Ray 的 lifecycle 差异；
- host sampling 和设备同步；
- TPU generation、topology 与量化支持差异；
- release/nightly feature matrix 不可混用。

## 证据结论

- plugin、runner、JAX/PyTorch 路径和 platform hook：`SOURCE_IMPLEMENTED`。
- repository release/nightly model、feature、kernel 和 parallelism tables：`RELEASE_CONTRACT`。
- TPU 规格：官方硬件文档，但具体性能仍是 `VENDOR_CLAIM`。
- 本地 runtime correctness、compile latency、abort/failure 和服务性能：`UNKNOWN`。
