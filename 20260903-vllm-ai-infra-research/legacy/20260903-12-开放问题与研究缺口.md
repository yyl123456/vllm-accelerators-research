# 开放问题与研究缺口

## 通用 P0

1. `Executor.execute_model(non_block=True)` 返回的 Future 是否对所有 backend 都保证真实设备完成，而非 host submit 完成？`UNKNOWN`。
2. 是否存在同一 Engine 内跨供应商 worker 的已支持反例？源码平台解析为单选，但官方长期 contract 未确认。
3. `Platform`、SchedulerOutput、KV interface、attention backend 是否有明确 public compatibility/deprecation policy？未发现统一稳定 ABI 承诺。
4. 各 plugin 在 abort/preemption 时是否等待 in-flight device write 后才复用 block？没有真实硬件证据。
5. general plugin 的 import-time patch/runtime 初始化在 fork、Ray、热重启中是否可重复？各 backend 需独立验证。

## Ascend

- 57 个 patch 中哪些触及 stateful request/KV/sampling/collective 路径，哪些只是兼容或性能 patch？需要生成精确 patch→upstream symbol map。
- CANN/HDK/ops/HCCL/torch-npu/vLLM-ascend 的当前完整 release tuple。
- ACLGraph 不同模式下的 capture key、cache 失效和 failure fallback。
- HCCL timeout 后 EngineCore、worker 和 KV pool 的恢复边界。
- 不同 A2/A3/310P 等 SKU 的实际支持差异。

## QAIC

- AoT QPC manifest/cache key 是否覆盖模型、量化、shape、SDK、firmware、topology 和 plugin revision。
- compiled profile 外的请求是 padding、拆批、拒绝还是重新编译。
- KV 在 session 内的物理 layout、可寻址性和 connector 一致性。
- Eager 与 AoT 的错误恢复、device reset 和 whole-process restart 边界。
- 多卡 TP/PP/P-D 的真实 topology、collective 和性能证据。

## Tenstorrent

- 当前 release 中 TT plugin、tt-metal、model bundle、firmware 和 vLLM 的准确 tuple。
- trace key 是否包含 topology、shape、KV address、runtime/firmware。
- group-string physical device ID 的所有上游 consumer 是否安全。
- prefix cache、cancel、preempt、structured output 在各模型 capability 下的硬件测试。
- 多 host 支持与 failure isolation。
- NoC/SRAM 对 decode、长上下文、MoE 的实际 trace 和 workload 性能。

## TPU

- JAX 与 TorchAX 路径共享和不共享的 canonical IR、weight、KV 与 compile cache 边界。
- XLA executable cache 的 shape/topology/runtime key 与 miss 行为。
- Raiden/jaxlib 双 XLA、Pathways 和 multiprocess/Ray 的 lifecycle test。
- prefix cache、preemption、P/D connector 的物理 KV 可迁移性。
- sampling/RNG/logprobs 在 host/device 与双 frontend 间的一致性。
- ICI 与 DCN 的 vLLM workload 实测，而非网络峰值。

## 性能研究缺口

本次没有可比较的同 workload 测试。后续若有硬件，应统一：

- 相同模型 revision、tokenizer 和可接受精度；
- 明确量化而非强求完全相同 dtype；
- 输入/输出长度分布与 prefix reuse；
- arrival rate、并发和 SLO；
- TTFT、TPOT/ITL、E2E、throughput、功耗；
- compile/warmup 是否计入；
- 单卡/多卡 topology；
- 失败率和长稳时间。

只有这些条件完整，才适合做架构选型而非展示性 benchmark。
