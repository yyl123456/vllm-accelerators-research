# AI 加速器架构与推理影响

## 比较方法

芯片规格只有映射到 serving workload 才有意义。本章按计算、存储、数据移动、执行模型、编译、互连和系统软件比较；不以峰值 FLOPS/TOPS 排名。

## 硬件快照

| 平台 | 计算组织 | 主要设备内存 | 互连/主机 | serving 关键约束 |
|---|---|---|---|---|
| NVIDIA GPU | SIMT + Tensor Core | HBM/GDDR + shared memory/cache | PCIe/NVLink/NVSwitch | 动态 kernel 丰富，decode 常受带宽和 launch 影响 |
| Ascend | Cube/Vector/Scalar；部分产品 AIC/AIV 分离 | GM + L1/L0/UB | PCIe/HCCS/RoCE，HCCL | Cube/Vector 与 DMA 流水；ACLGraph/算子覆盖/版本 tuple |
| QAIC Ultra | AI cores/NSP，面向 inference | 128GB LPDDR4x + 576MB SRAM | PCIe 4 x16 | 大容量低功耗；AoT shape/artifact 与动态调度折衷 |
| Tenstorrent Wormhole n300 | Tensix grid，FPU/SFPU + RISC-V dataflow | 24GB GDDR6 + 192MB 分布式 SRAM | PCIe + 片内/跨卡 Ethernet/NoC | 显式 tile/data movement、trace、mesh、模型专用实现 |
| TPU v6e | systolic MXU + vector/scalar | 32GB HBM/chip | 800GB/s ICI/chip，2D torus | XLA/SPMD、shape/compile、拓扑和 collective 共同决定效率 |

规格来源分别是 [Qualcomm Cloud AI 100 Ultra](https://www.qualcomm.com/data-center/products/cloud-ai-100-ultra)、[Tenstorrent Wormhole cards](https://docs.tenstorrent.com/aibs/wormhole/index.html)、[Google TPU v6e](https://docs.cloud.google.com/tpu/docs/v6e) 和 [Ascend C hardware abstraction](https://www.hiascend.com/document/detail/en/canncommercial/850/opdevg/Ascendcopdevg/atlas_ascendc_10_0015.html)。这些数字是 `VENDOR_CLAIM`，不是同 workload 测量。

## Prefill 与 Decode

Prefill 可形成较大的 GEMM，通常更容易接近矩阵单元峰值；Decode 的 batch 和并发不足时，单步矩阵变窄，权重与 KV 数据移动、同步和调度开销更突出。

因此：

- 高 FLOPS 不保证低 TPOT；
- 大容量支持大模型，但低带宽可能限制 decode；
- 大片上 SRAM 只有在软件显式复用、分片和流水时才能转化为收益；
- 高速互连更利于 TP/EP，但拓扑映射不佳仍会造成热点；
- 静态 graph 减少 host overhead，却可能增加 padding 和 shape cache。

## 存储层次对 KV 的影响

KV Cache 容量近似随层数、KV heads、head dimension、dtype 和 token 数线性增长。硬件的内存层次决定 KV 的物理策略：

- GPU/Ascend/TPU 常以大容量 device memory 为主，并用 kernel/graph 访问 block table；
- QAIC AoT 需要把 KV shape、compiled context length 和 session artifact 一起考虑；
- Tenstorrent 的分布式 SRAM 与 GDDR 通过 NoC 显式搬运，KV layout 与 model program 更强绑定。

片上 SRAM 更像工作集/流水 buffer，而非自动成为完整长上下文 KV pool。

## 执行模型

### Eager kernel

优点是动态性强、调试直接；缺点是 launch、Python/host packing 和同步可能成为 decode 瓶颈。

### Capture/replay

CUDA Graph、ACLGraph 和 TT trace 复用已捕获的执行序列与地址关系。适合稳定 decode shape，但需要 warmup、capture sizes、固定 buffer 和失败回退。

### AoT/XLA graph

QAIC AoT 和 TPU/XLA 可做跨算子优化及静态内存规划。scheduler 必须了解 shape bucket、padding、compile miss 和 topology，否则服务层的动态 batch 会不断破坏编译收益。

## 互连与并行

- PCIe-attached 单卡扩展不等同于 coherent 多卡大内存。
- TP 的 collective 频率使互连延迟和 topology 成为首要变量。
- EP 需要 all-to-all，且负载取决于 token routing。
- TPU ICI、Ascend HCCS/HCCL、Tenstorrent Ethernet mesh、NVLink/NVSwitch 都有不同拓扑与 collective 实现。
- 跨 host 后，控制面、故障域、NIC 和 KV transfer 会比单 kernel 性能更重要。

## 架构决策矩阵

| 问题 | 动态 GPU-like | Graph/AoT | Dataflow/model-owned |
|---|---|---|---|
| 请求形状 | runtime packing | bucket/padding/compile | program/trace/model capability |
| 调度器 | token budget | 应感知 shape | 常需 phase/model 特定策略 |
| KV | 通用 block allocator | layout 是 artifact 契约 | 模型/runtime 决定物理布局 |
| sampling | host/device 均可 | 需纳入 graph 或 D2H | 依模型能力声明 |
| 升级风险 | kernel/API drift | compiler/artifact tuple | model adapter/runtime tuple |
| 调试 | kernel profiler | graph/compiler profiler | trace/NoC/program profiler |

## 不能从规格推出的结论

- 峰值算力不能推出 vLLM 吞吐。
- memory bandwidth 不能推出 TTFT 或 TPOT。
- 容量能容纳权重不能推出 KV、workspace 和并发也能容纳。
- 有高速互连不能推出某个 collective 已优化。
- 有 graph runtime 不能推出 dynamic batching 无重新 capture/compile。
