# Subagent 架构质询记录

## 方法

本研究使用同一个只读“苏格拉底式架构审查 Subagent”。它不写文档、不作完成声明，只负责提出能改变架构判断的问题。主 Agent 回到固定 revision 源码和官方资料回答。每个问题按 P0/P1/P2 分级。

## Topic A/B/C：三轮质询

### 第一轮：职责、状态与接口

主要问题：

1. 请求状态分别存在 API、OutputProcessor、EngineCore、Scheduler 和 Worker，权威状态在哪里？
2. `SchedulerOutput` 是后端无关执行 IR，还是包含 GPU batch/block table 假设的内部结构？
3. 逻辑 KV block、物理 allocation 和 attention layout 如何协作与 rollback？
4. `execute_model(non_block=True)` 后 abort/free 如何与 in-flight device work 排序？
5. token budget 是否足以描述 prefill/decode/speculative/multimodal 成本？
6. Platform 是否混合了 detection、policy、compile、communication 与 lifecycle？
7. OOT plugin 能否避免 import GPU 实现完成全链路？
8. plugin probe 的 import-time side effect 和多进程一致性如何保证？
9. 单 platform 选择对异构 deployment 意味着什么？

结论变化：把“插件接口存在”降级为发现机制；要求逐层验证 control/execution/model/release plane。

### 第二轮：四种实现范式

主要问题：

- Ascend global patch 是否覆盖所有入口；57 个 patch 哪些触及状态路径？
- Ascend/QAIC 继承 GPU runner 时实际复用了哪些 GPU-specific 成员？
- TT 自有 scheduler/engine 是硬件必要性还是历史选择？
- QAIC AoT artifact key 是否完整？
- TPU unified lowering 是否真的统一 IR、权重和 KV？
- sampling/RNG 与异步 completion 是否保持 vLLM 外部语义？
- plugin 如何管理 upstream API drift？

结论变化：不再以代码量推导硬件适配难度；将接入年代、目标 feature 和上游 API 成熟度列为共同因素。

### 第三轮：反例和证据降级

Subagent 要求以下主张降级：

- “跨供应商只能外部路由”是 `RECOMMENDATION/INFERENCE`，不是官方禁止。
- KV 逻辑/物理双重所有权只作为 upstream V1 的 `SOURCE_IMPLEMENTED`，vendor 需逐一验证。
- Future 是否代表真实设备完成仍为 `UNKNOWN`。
- 实现范式由硬件决定只能是部分推断，不能作单因果结论。
- CUDA 引用不能一概称为不可移植；需区分隔离的 fast path 和共享耦合。
- 内部 dataclass 没有发现 public ABI 承诺，但不能仅据此证明未来必然不稳定。

Topic A/B/C 在文档级达到饱和；运行时成熟度转入 vendor topic。

## Vendor Topic：质询主轴

该 Topic 同样进行三轮：第一轮逐 backend 寻找会改变架构判断的问题；第二轮专门攻击版本 tuple、组合特性、异步完成与故障语义；第三轮要求将无硬件证据的结论统一降级。

### 通用

- 是否有完整的 vLLM/plugin/runtime/compiler/driver/firmware/model/quant/container tuple？
- 标称内存扣除权重、KV、workspace、communication 和 runtime reservation 后剩多少？
- 是否有同 workload 的 TTFT/TPOT/throughput/功耗测量？

### Ascend

- Cube/Vector/DMA 分别由 runner、compiler、custom op 和 CANN 哪层控制？
- stateful patch 是否按 CANN/SKU/model/graph mode guard？
- HCCL completion/failure 如何映射到 batch 和 KV free？
- graph 对 mixed batch、chunked prefill 和 shape 的策略是什么？

### QAIC

- Eager/AoT 是否是两个不同产品面而非性能开关？
- QPC artifact 和 compiled profile 外请求如何处理？
- LPDDR/SRAM/PCIe 下 KV 和 host staging 的真实布局是什么？
- session/device failure 是否只能重启进程？

### Tenstorrent

- N300/T3K mesh 如何映射权重、KV、trace 和 ttnn placement？
- 自有 scheduler 是否保持 cancel、streaming、prefix 和 preemption 外部语义？
- trace key 和 failure fallback 是什么？
- group-string device ID 是否被所有消费者正确理解？

### TPU

- v6e topology 如何映射 SPMD partition、KV 和 collective？
- XLA shape/bucket/cache miss 如何影响 admission？
- KV 是否支持 vLLM prefix/preempt/P-D 的可寻址与可迁移语义？
- sampling 和 RNG 在 JAX、TorchAX、host/device 间如何一致？

### 第二轮：反例与故障语义

- Ascend feature matrix 中单项支持是否能组合，graph eager fallback 的 shape 和数值边界在哪里？
- QAIC 的 QPC 未命中 profile 时是拒绝、重编译还是 fallback，这个决策是否会隔离租户资源？
- TT async future 何时表示 readback/finalization 完成，placeholder 遇到 preemption/reset 如何避免重放？
- TPU XLA executable/cache 未命中时，admission 是否把 compile latency 和内存峰值纳入预算？

这一轮促使文档把“正常路径存在”和“取消、抢占、reset、超时与部分失败安全”分开记录。

### 第三轮：证据降级与饱和判定

Subagent 最终认为，静态源码和公开文档已不再能消除以下问题：真实数值与 API 正确性、多设备通信正确性、abort/failure rollback、真实 shape/fallback 行为和服务性能。继续追问只会重复同一证据缺口，因此 Vendor Topic 在文档级判定为饱和，剩余项目统一进入 `UNKNOWN` 和后续硬件验证清单。

## 已纳入文档的审查规则

- 所有硬件数字都标来源，不推导无条件性能。
- QAIC Eager/AoT 分开描述。
- Qualcomm 范围只覆盖 Cloud AI 100/80。
- TPU unified 仅描述共同目标，不声称所有表示相同。
- TT chip-count compatible 不等于 mesh validated。
- Ascend feature matrix 不等于任意 feature 组合支持。
- 无硬件验证的 abort、preempt、failure、correctness 和 performance 均为 `UNKNOWN`。
