# vLLM 平台抽象与第三方插件机制

## 插件发现

vLLM 使用 Python entry point：

- `vllm.platform_plugins`：返回 Platform 类路径；
- `vllm.general_plugins`：执行模型、connector、loader、endpoint 等注册和 process-local patch。

平台探测函数应当是可重复调用、低副作用的 capability probe。当前 `resolve_current_platform_cls_qualname()` 收集所有激活结果并要求唯一平台；一个 OOT platform 优先于 builtin，但多个同类激活会报错。

## Platform 的实际职责

`vllm/platforms/interface.py:Platform` 同时承载：

- 设备类型、dispatch key、可见设备环境变量；
- Ray resource 和设备 ID 映射；
- dtype、quantization、attention 能力；
- compile backend、pass manager、IR/C kernel import；
- communicator、worker、executor、punica 等类选择；
- memory、seed、inference mode 和 config 校验；
- static graph、hybrid KV、sleep mode 等 feature gate。

`INFERENCE`：它是 capability registry、factory、compatibility adapter 和 lifecycle glue 的组合，不是纯粹的硬件描述。新增硬件经常还需 general plugin 和 runner/scheduler 扩展。

## 四种接入范式

| 后端 | 主要形态 | 控制权位置 | 主要风险 |
|---|---|---|---|
| Ascend | OOT Platform + global patch + `GPUModelRunner` 派生 | vLLM 主体，plugin 深度修补 | 私有 API drift、import 顺序 |
| QAIC | OOT Platform + eager/AoT Worker/Runner | vLLM 调度，vendor 执行 session | artifact/shape tuple、双模式依赖 |
| TPU | Platform + native runner + JAX/PyTorch/XLA | vLLM 调度与 XLA/SPMD runtime 分工 | runtime 生命周期、shape compilation |
| Tenstorrent | Platform + 自有 scheduler/engine/runner + tt-metal model | vendor model/runtime 获得更多控制 | 重复实现、上游升级、非标准 topology mapping |

范式差异不能直接解释为硬件优劣或适配工作量。它同时受到接入年代、上游 API 成熟度、目标 feature 和 release 策略影响。

## Platform 不足以表达的内容

常见额外需求：

- scheduler 的 token/shape/admission policy；
- 模型级 `max_tokens_all_users` 或 graph bucket；
- device-side sampling 和 async decode；
- KV transfer connector 与定制 KV spec；
- process-wide runtime 初始化；
- model registry 和 vendor-specific model adapter；
- monkey patch 上游内部符号。

这些需求说明“硬件可插拔”至少包含 control plane、execution plane、model plane 和 release plane 四层。

## 兼容性

entry point 名称稳定不意味着内部接口稳定。`SchedulerOutput`、GPU runner 成员、KV interface、compile hooks 和 process topology 都可能随版本变化。每个 plugin 必须：

1. pin vLLM revision/release；
2. 在所有进程入口加载 general plugin；
3. 对 online/offline、uniproc/mp/Ray 做 discovery 测试；
4. 用真实硬件 CI 验证 feature matrix；
5. 发布 runtime/driver/compiler/model 的完整 tuple。

## 单平台边界

当前一个 EngineCore 解析出一个 `current_platform`，并据此选择 worker、communicator、attention 和 compilation。异构硬件混合到同一 Engine 并非当前通用契约。

推荐架构是：每种平台独立 Engine/Deployment，由上层 router 决定请求去向；如需 P/D 分离，使用显式 KV transfer 协议。这样故障域、版本 tuple 和 capacity model 均可独立管理。

## 新插件最小验收

- 无硬件时不会误激活；有硬件时所有相关进程选择一致。
- 不依赖未声明的 CUDA library/import side effect。
- config 在模型加载前完成验证。
- worker 能报告容量和 KV spec，EngineCore 能建立一致 layout。
- execute/completion/free 的时序明确。
- sampling、seed、logprobs、structured output 行为一致。
- abort/preempt/failure 能回收所有逻辑与物理状态。
- 支持矩阵区分代码存在、release 承诺和真实硬件测试。
