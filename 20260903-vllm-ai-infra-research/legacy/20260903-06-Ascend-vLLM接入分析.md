# Ascend vLLM 接入分析

## 结论

`vllm-ascend` 是社区维护的 OOT hardware plugin，但其实现不是轻量 Platform shim。固定 revision 同时注册 platform、KV connector、model loader、profiling 和模型，并在 EngineCore 子进程等位置执行 process-wide patch。它复用 vLLM V1 控制面，同时深度接管 NPU graph、attention、通信、量化、scheduler 变体和模型能力。

## 软件栈

```text
vLLM API / EngineCore / Scheduler
        ↓
vllm-ascend Platform + patches + NPUModelRunner
        ↓
torch-npu / Triton Ascend / custom ops
        ↓
CANN: ACL runtime + ACLGraph + operator/compiler stack
        ↓
HCCL/HCOMM + driver/firmware
        ↓
Ascend AI Core / HBM / HCCS-RoCE-PCIe
```

官方 CANN 文档把 ACL runtime 定义为 device、memory、context、stream、event、kernel 与 graph 管理层；HCCL 支持 AllReduce、AllGather、ReduceScatter、AlltoAll 及 HCCS/RoCE/PCIe。[CANN Runtime](https://www.hiascend.com/eng/cann/runtime)；[HCCL overview](https://www.hiascend.com/document/detail/en/canncommercial/850/commlib/hcclug/hcclug_000001.html)

## Plugin 边界

`SOURCE_IMPLEMENTED`：

- `vllm.platform_plugins`: `ascend = vllm_ascend:register`；
- general plugins 注册 KV connector、netloader/rfork loader、service profiling 和模型；
- `_ensure_global_patch()` 在相关进程执行 `adapt_patch(is_global_patch=True)`；
- `NPUPlatform` 使用 `PrivateUse1` dispatch key、`ASCEND_RT_VISIBLE_DEVICES`、`NPUCommunicator`；
- 编译 hook 返回 `AscendCompiler`，static graph wrapper 返回 `ACLGraphWrapper`；
- `NPUModelRunner` 继承上游 `GPUModelRunner`；
- 源码含 57 个 patch Python 文件，说明兼容面跨越多个内部组件。

因此“hardware pluggable”在部署层成立，但维护层仍接近一个随上游演进的适配分支。不能仅以 OOT package 推断低耦合。

## 硬件到软件的映射

Ascend AI Core 抽象包含 Cube、Vector、Scalar、local/global memory 和 DMA。部分产品为 Cube/Vector 分离架构：矩阵和向量核各有控制与存储路径，数据可经 GM 交换。[Ascend hardware architecture](https://www.hiascend.com/document/detail/en/canncommercial/850/opdevg/Ascendcopdevg/atlas_ascendc_10_0015.html)

对 LLM 的影响：

- GEMM/MoE 需要 Cube 高利用率；softmax、norm、sampling 等依赖 Vector；
- layout conversion 和 Cube/Vector 间的数据搬运可能抵消 fusion 收益；
- MTE/DMA 与计算的 overlap 是 kernel 调优核心；
- TP/EP 需要将 HCCL graph/single-op 模式与计算图协调；
- 不同 Ascend 产品可能是耦合或分离架构，不能用单一 910 结论覆盖全部 SKU。

## Graph 与动态 serving

`RELEASE_CONTRACT`：仓库文档说明 V1 支持 ACLGraph capture/replay，并有 FULL、FULL_DECODE_ONLY、PIECEWISE 等模式；`Npugraph_ex` 可在 capture 前做 FX fusion；static kernel 可带来数分钟到数十分钟启动编译成本。

架构权衡：

- uniform decode 最适合 full graph；
- mixed prefill/decode 更依赖 piecewise；
- capture size 越多，启动和 graph resource 压力越大；
- attention backend 只支持 uniform batch 时，配置会被缩窄；
- graph mode 的命名沿用 `cudagraph_mode`，这是一处 CUDA 历史语义泄漏，但运行机制实际是 ACLGraph。

## 调度和 KV

平台配置会按 graph、异步、recompute、Dyntra load balancing、short-request-first 等条件选择 scheduler。仓库还包含 KV pool、CPU offload、layerwise/sparse offload、Mooncake 和 P/D connector。

这说明 Ascend 适配已经从“设备执行”扩展到资源管理与集群 serving。另一方面，组合矩阵中仍有 partial、unknown 和 mutually exclusive 项；不能把单项支持叠加成任意组合支持。

## 版本与 release tuple

当前 requirements 固定 `torch==2.10.0` 与 `torch-npu==2.10.0.post4`。部署还需匹配 vLLM、vllm-ascend、CANN、driver/HDK、ops package、设备 SKU 和模型。CANN 9.0 release notes 本身包含 toolkit、ops、HCCL、ATB 等子包映射，进一步说明“只固定 Python wheel”不够。

## 主要风险

- global patch 对上游私有符号敏感；必须覆盖 API server、EngineCore、worker、Ray/mp 等所有进程入口。
- `GPUModelRunner` 继承既复用通用 batch state，也可能继承 GPU-specific fast path。
- graph capture、动态 shape、attention backend 和 feature 组合存在相互限制。
- release notes 中的支持不能代替目标模型/精度/拓扑的硬件回归。
- CANN/driver/ops 不匹配可能表现为 kernel 或 runtime 故障，而不是清晰的 Python dependency error。

## 证据结论

- Plugin 与核心组件：`SOURCE_IMPLEMENTED`。
- 官方功能矩阵和 graph 模式：`RELEASE_CONTRACT`。
- 本地正确性、abort/preemption、故障恢复、性能：`UNKNOWN`。
- “深度 patch 增加版本维护成本”：`INFERENCE`，由 patch 面和内部继承支持，但未量化实际升级成本。
