# 异构后端横向比较与决策矩阵

## 接入形态

| 维度 | Ascend | QAIC | Tenstorrent | TPU |
|---|---|---|---|---|
| 接入包 | `vllm-ascend` | `vllm-qaic` | `vllm-tt-plugin` | `tpu-inference` |
| Platform | OOT | OOT | OOT | OOT/TPU enum |
| 控制面复用 | 高，但有大量 patch/scheduler 变体 | vLLM scheduler 为主 | 自有 scheduler/engine 较多 | vLLM scheduler + 自有 DP scheduler |
| Runner | `GPUModelRunner` 派生 | Eager/AoT 均派生 GPU runner | native TT runner | native TPU runner |
| 编译/执行 | torch-npu、AscendCompiler、ACLGraph | torch-qaic 或 QPC AoT | TTNN/TT-Metal program/trace | JAX/TorchAX→XLA/PJRT |
| KV capacity | device profile + Ascend spec/connector | session/profile，AoT shape 强约束 | 模型声明 token pool | 聚合 TPU device memory + TPU KV spec |
| 通信 | HCCL/HCOMM | QAIC device/QID collective | NoC/Ethernet mesh | XLA/SPMD + ICI/Pathways |
| 版本策略 | plugin/CANN/torch-npu 矩阵 | 模式和 branch 强绑定 | vLLM pin + tt-metal/model tuple | release/nightly + libtpu/JAX tuple |

## 共同难点

### 1. 内部 API 漂移

四种插件都不只依赖稳定 entry point；它们消费 Platform hooks、SchedulerOutput、worker lifecycle、model runner、KV interface 和 attention registry。升级风险与改动触及的状态面有关，不能只用 LOC 衡量。

### 2. 动态请求与规则执行

- Ascend：ACLGraph capture sizes 和 attention graph compatibility；
- QAIC：compiled context lengths/QPC；
- TT：纯 prefill/纯 decode step 与 trace/model program；
- TPU：XLA shape、SPMD sharding 与 compile cache。

四者都说明 scheduler 需要理解不止 token 数的执行成本。

### 3. KV 生命周期

每种平台必须保持请求 token progress、逻辑 block、物理 KV tensor/session buffer 和完成事件一致。存在 connector 或 prefix-cache 代码不等于 abort、preemption 和 failure 已经安全验证。

### 4. 版本 tuple

共同部署单元应写成：

```text
model+weights+quantization
× vLLM
× plugin
× framework/compiler/runtime
× driver/firmware
× device SKU/topology
× container/build flags
```

## Feature 证据矩阵

以下是源码/仓库文档层的概括，不是同 revision 的硬件实测。

| 能力 | Ascend | QAIC Eager | QAIC AoT | TT | TPU |
|---|---|---|---|---|---|
| continuous batching | 有 | 有 | 有，受编译 shape 约束 | 有，但 step phase-homogeneous | 有，受 XLA shape 约束 |
| mixed prefill/decode | graph/backend 相关 | 待 tuple 验证 | bucket/session 相关 | 当前明确不支持同 step 混合 | 待 shape/runtime 验证 |
| prefix cache | 文档支持，组合受限 | 计划/不支持 | 计划/不支持 | 模型 capability gate | feature matrix 绑定 release |
| chunked prefill | 文档支持 | 待验证 | profile 相关 | 仅可恢复 prefill 的模型 | feature/shape 相关 |
| speculative decode | 多路线 | 不支持或有限 | 支持多路线 | 模型相关 | release/nightly 相关 |
| LoRA | 支持，组合受限 | 不支持 | 支持，组合受限 | 模型/路径相关 | 支持矩阵 |
| multimodal | 支持，KV pool 有限制 | experimental | 支持 | 多个 TT model adapter | 支持矩阵 |
| TP | HCCL | QID | QID | mesh/model mapping | SPMD/mesh |

## 选型决策

### 目标是最大程度复用 vLLM 功能

优先选择 Platform/Worker/Attention 的窄适配，但前提是硬件可以消费 vLLM 的动态 batch 与 KV contract。不能为了表面复用而把 CUDA 行为藏在 monkey patch 中。

### 目标是发挥静态编译器能力

QAIC AoT、TPU/XLA 和 Ascend graph 需要把 shape/bucket/compile feedback 暴露给 admission control。建议将 compile profile 作为 scheduler resource，而不是仅在 runner 内 padding。

### 目标是模型/runtime 深度联合优化

TT 风格的 model-owned executor 能表达 trace、mesh 和物理 KV，但应最小化对 EngineCore 外部语义的偏离，并对 request lifecycle 建立 conformance test。

### 目标是跨供应商异构 serving

当前源码显示一个 Engine 只选择一个 `current_platform`。`RECOMMENDATION`：以独立 deployment 形成故障和版本域，在上层路由；P/D 分离时使用显式 KV transfer。没有官方合同证明“只能如此”，所以这是当前最安全方案而非永久限制。

## 扩展生态

- CUDA、ROCm、CPU、XPU 当前是 vLLM builtin platform。
- Intel Gaudi、AWS Neuron、IBM Spyre、Apple Silicon 等存在 OOT device plugin。
- Gaudi 文档显示同样使用 platform + general custom-op entry point，并提供版本化容器，是本报告四种范式之外的重要参照。
- Spyre 的 scheduler 文档表明静态硬件可能需要 `batch_size × max_tkv` ceiling、chunk alignment 和 padding，再次验证 token-only scheduler 的局限。

这些扩展后端只做生态扫描，未完成与四个主后端同深度的 revision 审计。

## 架构师检查单

1. 支持结论属于 source、release、runtime 还是 performance？
2. model/quant/context/concurrency/topology 是否完整？
3. scheduler 是否知道真实 shape 和内存成本？
4. completion 是否意味着设备完成，还是只完成 host enqueue？
5. abort/failure 后何时才能复用 KV slot？
6. sampling 和 RNG 在哪里？
7. artifact cache 如何失效？
8. plugin 在所有子进程是否一致加载？
9. 多卡通信与 rank/topology 如何映射？
10. 能否通过完整镜像/release manifest 重建？
