# Scheduler 请求状态机

## 本篇唯一主问题

vLLM V1 Scheduler 如何表示一个请求从 waiting 到 running、preempted、finished 或 streaming pause 的状态转移，哪些字段决定语义 progress？

## In scope

`Request`、`RequestStatus`、waiting/running/skipped queues、structured-output/remote-KV/streaming 等待态、schedule/update 转移和 events。

## Out of scope

不讨论 token budget 数值选择，不展开 KV block allocator，不解释 frontend detokenization 或物理 device completion。

## 证据锚点

- `vllm/v1/request.py`：`Request`、`RequestStatus`、progress/in-flight/streaming fields。
- `vllm/v1/core/sched/scheduler.py`：`add_request()`、`schedule()`、`update_from_output()`、preempt/finish/free。
- `vllm/v1/core/sched/request_queue.py`：FCFS/priority queue。
- `vllm/v1/core/sched/output.py`：对 runner 的状态 delta。

## 状态集

`RequestStatus` 在固定 revision 中包含：

```text
WAITING
WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR
WAITING_FOR_REMOTE_KVS
WAITING_FOR_STREAMING_REQ
RUNNING
PREEMPTED
---------------- finished threshold ----------------
FINISHED_STOPPED
FINISHED_LENGTH_CAPPED
FINISHED_ABORTED
FINISHED_IGNORED
FINISHED_ERROR
FINISHED_REPETITION
```

`RequestStatus.is_finished()` 使用枚举顺序：位于 `PREEMPTED` 之后的值视为 finished。这是一个源码不变式；在枚举中插入新状态时必须考虑这个顺序契约。`SOURCE_IMPLEMENTED`

## Request 中的 progress 不是单一计数器

| 字段/概念 | 含义 | 不可互换的原因 |
|---|---|---|
| `num_prompt_tokens` | 正规化后 prompt 长度 | 不包含 output |
| `output_token_ids` | 已接受输出历史 | 不包含 spec/stale placeholder |
| `spec_token_ids` | draft 候选 | 尚未提交 |
| `num_computed_tokens` | scheduler 认为已计算的 progress | async/PP 可乐观包含 in-flight |
| `num_output_placeholders` | 已预留但输出未应用的步 | 不是用户 token |
| `num_in_flight_tokens` | 已提交尚未处理的 token work | 需 completion/update 才可退休 |
| `num_stale_output_tokens`/`drop_stale_output` | preemption/reset 下的 stale result 语义 | 必须区分“交付但不更新 reset counter”和“完全丢弃” |
| `last_sched_seq` | 最近调度序列 | 用于延迟 block free，不是 token position |

本质上，Scheduler 同时跟踪 logical progress、speculative progress、reserved progress 和 externally committed output。任何 vendor scheduler 如果只保留 `num_computed_tokens`，都容易在 async/preemption/spec 路径中错误重放。

## Waiting 不只是“没有空闲 GPU”

waiting 原因包括：

- 尚未被 token/KV/input/encoder budget 接管；
- structured-output grammar 未就绪；
- remote KV/encoder cache 尚未可用；
- streaming request 等待更多输入；
- preempted 后等待重建资源；
- 在当前轮被 `skipped_waiting` 暂存，以允许后续请求继续尝试。

`schedule()` 在某个 running request 因 encoder/cache/alignment 等原因得到 0 token 时可以 `continue` 而不是 `break`，注释明确这会不严格遵循 FCFS，让后续请求获得机会。`SOURCE_IMPLEMENTED`

因此“FCFS scheduler”的真实语义是优先顺序，不是头部阻塞下的绝对服务次序。

## Running 表示可参与调度，不表示 device 此刻正执行

running list 是 scheduler 中的活动 request 集合。某 request 可因 token budget、PP cadence、prefill throttling、encoder budget、Mamba alignment 或 async max-token guard 在某 step 不被选中。

反之，已移出 running 的 preempted/finished request 仍可有 in-flight device output。所以 scheduler membership 不能代替 device activity/completion 跟踪。

## Priority 比较契约

`Request.__lt__()` 的顺序是：

1. priority 数值；
2. arrival time；
3. request ID；
4. Python object identity 作为最后 tie-breaker。

priority scheduling 在 KV 不足需要 preempt victim 时，会选择较低优先级/较晚到达的 running request，并修正本轮已消耗的 token/input/encoder 预算。这是 scheduler-local priority，不证明有 tenant weighted fairness 或 deadline scheduling。

## Finished 映射

finished status 映射到 `FinishReason`：

- stopped → `stop`；
- length capped/ignored prompt → `length`；
- aborted → `abort`；
- error → `error`；
- repetition → `repetition`；
- `WAITING_FOR_STREAMING_REQ` 在某些完成映射中对应 `stop`。

streaming input 请求可以在一个 chunk 结束后等待更多 input，所以“本次输出有 finish reason”与“整个 session object 已销毁”不总是同一件事。

## Events 不是跨进程全局时钟

core request 可积累 `QUEUED/SCHEDULED/PREEMPTED` events，使用 `time.monotonic()`。源码注释指出这些 timestamp 只用于 frontend 计算 core events 之间的 interval，不应与其他进程 timestamp 直接比较。`SOURCE_IMPLEMENTED`

跨 gateway/frontend/core/worker/device 的时间归因需要 tracing 与 clock-domain 设计，不能把这些 event 直接当端到端时间线。

## 主要不变式

1. finished status 不再回到 running；streaming continuation 必须通过明确 session 协议。
2. output history 只包含已接受/提交 token，spec/stale placeholder 分开。
3. 一个 request 不同时作为 waiting 和 running 的权威成员；temporary skipped queue 需按 policy 恢复顺序。
4. preemption 需记录已产生但尚未退休的 output，不能只将 status 设为 `PREEMPTED`。
5. runner 中的 request/input-slot 副本必须根据 `SchedulerOutput` 的 new/cached/resumed/finished delta 同步。

## 架构决策点

1. 新 backend scheduler 是复用这个状态机，还是只复用 API 外观？
2. 它如何表示 spec、async、PP 和 preemption 的未提交 progress？
3. 某个 waiting 原因是否有独立 metrics，还是全部看起来像 queue delay？
4. priority 是业务 SLO 语义还是 scheduler-local sort key？
5. streaming session 的 chunk finish 和 session finish 如何区分？
6. core events 如何与 frontend/device clock domain 关联？

## 证据结论

状态集、排序规则、progress fields、waiting/running 调度和 finished mapping 为 `SOURCE_IMPLEMENTED`。它们在所有 vendor backend、故障和功能组合下的语义一致性尚需 runtime 验证。
