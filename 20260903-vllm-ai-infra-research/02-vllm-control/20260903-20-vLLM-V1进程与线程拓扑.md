# vLLM V1 进程与线程拓扑

## 本篇唯一主问题

vLLM V1 在不同 executor/DP 配置下由哪些前端、EngineCore、worker 进程与后台线程组成，状态和故障边界在哪里？

## In scope

`AsyncLLM/LLMEngine`、`EngineCoreClient`、`EngineCoreProc`、Executor、Worker 的进程/RPC 边界，输入输出通道，DP engine 关系和关停故障域。

## Out of scope

不解释 scheduler 算法、KV 分配、worker 内部 model runner、Ray placement 细节或 HTTP 协议。

## 证据基线

- vLLM revision：`bb363db9a5ec2edc7b39e99b00af363a89d1fb81`。
- 核心文件：`vllm/v1/engine/async_llm.py`、`llm_engine.py`、`core_client.py`、`core.py`、`vllm/v1/executor/*`、`vllm/v1/worker/*`。
- upstream `docs/design/arch_overview.md` 将 V1 分为 API server、AsyncLLM、EngineCore、Executor、Worker、ModelRunner。[官方架构说明](https://docs.vllm.ai/en/latest/design/arch_overview/)

## 在线常见拓扑

```text
API server process
  asyncio request tasks
  AsyncLLM
    InputProcessor
    OutputProcessor + collectors
    EngineCoreClient
      input socket/queue  --------------------+
      output handler task/thread              |
                                               v
                                    EngineCoreProc process
                                      EngineCore
                                        Scheduler
                                        KV managers/connectors
                                        Executor
                                          | RPC/local call
                          +---------------+---------------+
                          v                               v
                     Worker rank 0                   Worker rank N
                       ModelRunner                     ModelRunner
                       device/runtime                  device/runtime
```

`AsyncLLM.__init__()` 在前端保留 `InputProcessor`、`OutputProcessor`，并通过 `EngineCoreClient.make_async_mp_client()` 建立背景 core 进程通道。因此 API/frontend request state 与 core scheduler request state 天然是两份副本，靠 request ID 和 core input/output 协议对齐。`SOURCE_IMPLEMENTED`

## Offline 同步拓扑

`LLMEngine` 仍通过 `EngineCoreClient` 与 core 交互，但上层由同步 `step()` 主动获取 `EngineCoreOutputs`、交给 `OutputProcessor.process_outputs()`，再把因 stop string 结束的 request abort 传回 core。

“offline”只改变 frontend 驱动方式，不意味所有 core/worker 都在同一进程，也不意味不使用 multiprocess executor。

## EngineCoreProc 的责任边界

`EngineCoreProc` 是 `EngineCore` 的进程容器，它负责：

- 接收 `ADD/ABORT/START_DP_WAVE/UTILITY` 等 `EngineCoreRequestType`；
- 驱动 engine loop 和 `EngineCore.step()`；
- 将 `EngineCoreOutputs` 发回正确 frontend client；
- 接收 executor permanent failure 哨兵信号；
- 管理关停、pause/wave 和 utility call 的进程边界。

`EngineCore` 本身保有 scheduler/executor/KV connector 等语义组件；`EngineCoreProc` 不应被理解为第二个 scheduler owner。

## Executor 拓扑选择

| Executor 形式 | 调用边界 | 适合解决的问题 | 新故障面 |
|---|---|---|---|
| UniProc | EngineCore 同进程直接调 Worker | 单 worker、低 IPC overhead | device fault 可直接影响 core |
| Multiproc | 本地 worker 子进程/RPC | 本机 TP/PP、进程隔离 | process liveness、queue/socket、shutdown |
| Ray | Ray actor/cluster transport | 多主机 placement 与 actor 管理 | control plane、network、actor loss |
| External launcher | 外部已创建 rank | MPI/torchrun/平台编排 | launcher 与 vLLM lifecycle 对齐 |

`Executor.get_class(vllm_config)` 由配置和 platform 选择实现。这是 backend 可以替换的边界，但 executor 并非只要能调用 `execute_model` 就完成；它还参与 worker init、memory profile、KV allocation、collective RPC、utility 和 shutdown。

## DP 不是一个全局 Scheduler

upstream 架构文档把每个 DP rank 视为一个 EngineCore，每个 core 有自己的 scheduler。`EngineCoreRequest.data_parallel_rank`、`client_index`、`current_wave` 等字段用于路由和 wave 协调。`EngineCoreOutputs` 中还有 `engine_index`、`wave_complete`、`start_wave`。

因此：

- 不能假定 DP 中所有 rank 共享 waiting/running queue；
- 某 rank 正在 prefill 不必意味其他 rank 做相同阶段；
- 全局公平、tenant quota 和负载均衡需要 DP coordinator/router 层语义；
- 一个 rank 的 KV/cache/compile warmness 不能从总体 device 利用率推断。

## 线程与后台任务

不应用“每进程一条线程”理解 V1：

- `AsyncLLM` 的 output handler 是 asyncio task；
- raw prompt/multimodal preprocessing 可通过 renderer executor 移出 event loop；
- multiprocess/ray executor 有控制和消息处理线程/任务；
- backend 可以用 thread pool 等待 deferred output，TT plugin 就显式有 async decode finalization；
- runtime/driver 自身可有 command queue、callback 和 background compiler thread。

线程数是实现细节，但是否在 event loop 上执行 blocking tokenization/readback/compile 是服务架构问题。

## 进程边界的序列化契约

`EngineCoreRequest`、`EngineCoreOutput(s)` 使用 `msgspec.Struct` 且有 array-like/omit-default 配置。部分新字段的源码注释要求追加到最后，以保持位置序列化兼容。`SOURCE_IMPLEMENTED`

这表明 internal transport 结构对字段次序有兼容性约束，但不构成面向 OOT plugin 的永久 public ABI 承诺。plugin 依赖这些内部类时仍需要绑定 vLLM revision 和 CI。

## 故障域

| 故障 | 直接影响 | 不能默认的恢复 |
|---|---|---|
| frontend request task | 单 stream/request | core work 自动取消 |
| API server process | 该 frontend 管理的 collector/connection | EngineCore 已提交 work 会被安全清理 |
| EngineCoreProc | 该 DP engine 的 scheduler/KV control | worker 可被无损重连并恢复 request |
| Worker/rank | 该 process group 的 device work | 只失败当前 request |
| collective group | 所有参与 rank | communicator 可继续使用 |
| output channel | frontend 可见 progress | device 没有继续写 KV/buffer |

V1 存在 executor failure sentinel 和 fault-tolerance 组件，但不能由 class 存在推导上表所有恢复都拥有 `EXPERIMENT_RESULT × STRESS_VALIDATED` 证据。

## 架构决策点

1. 前端与 core 是同一失效单元还是独立部署？
2. request ID/client index/DP rank/wave 如何保证输出返回正确 collector？
3. executor 是 local call、process RPC、Ray 还是 vendor-defined？它的 permanent failure 信号是什么？
4. 谁拥有长期 queue，谁能在进程失败后重建它？
5. DP rank 健康/缓存/容量是否作为独立路由信号？
6. blocking preprocessing/readback 是否发生在 API event loop？

## 证据结论

进程类、client/core transport、executor 实现和 DP 字段为 `SOURCE_IMPLEMENTED`。具体部署拓扑取决于配置与 platform；未在本次执行的进程失效恢复为 `UNKNOWN`。

## 本篇输出契约

后续控制面文档可假定 frontend/core/executor/worker 边界已定义，只需说明数据如何穿过它们。
