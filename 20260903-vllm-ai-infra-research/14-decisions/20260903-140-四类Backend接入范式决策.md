# 四类 Backend 接入范式决策

## 文档契约

- owner：Ascend、QAIC、Tenstorrent、TPU 的**接入范式**比较。
- 依赖输入：`70`–`74`、`100`–`135`。
- 唯一输出：选择 platform adaptation、runtime replacement 或 compiled artifact integration 的判断框架。
- 不讨论：逐功能支持、成本或上线门禁；由 `141`、`142`、`144` 持有。

## 四种实际范式

| Backend | 主要范式 | 核心适配面 | 最大耦合点 |
|---|---|---|---|
| Ascend | PyTorch/NPU platform + OOT patches/kernels | Platform、worker/runner、attention、ACLGraph、HCCL | 大量 upstream patch 与 CANN tuple |
| QAIC | Eager SDK path + AoT QPC artifact path | mode selection、session/QPC、固定 profile、KV/sampling | artifact profile 与 SDK/firmware ABI |
| Tenstorrent | OOT platform + TT-owned scheduler/runner/model generator | capability-driven config、lane scheduler、trace/async | vLLM scheduler semantics 与 model generator protocol |
| TPU | vLLM direct package detection + JAX/XLA unified lowering | JAX-native/TorchAX、SPMD、PJRT、compile manager | functionalization、shape specialization、runtime init |

这些不是优劣排序，而是阻抗位置不同。Ascend 尽量维持 PyTorch/vLLM GPU-like surface；QAIC 把部分工作提前到 QPC；TT 将更多 scheduling/model-runtime semantics 拉入插件；TPU 将两个模型前端统一到 JAX/XLA lowering。

## 决策问题

1. 硬件 runtime 是否能表达动态 batch、paged KV 和 request-local sampling？
2. 编译产物是否绑定 shape/profile/weight/SKU？
3. completion、buffer 与 communicator 是否有可映射到 EngineCore 的生命周期？
4. upstream abstraction 缺口应由 platform hook、custom worker/runner、scheduler replacement 还是 core change 修补？
5. OOT patch 数量是否已超过可持续升级阈值？

## 选择规则

- runtime 支持 PyTorch dispatch、动态 tensor 和 stream/event：优先窄 Platform/Worker/Attention adapter。
- runtime 只接受 profile-bound executable：将 artifact manifest、admission 和 miss policy 设为一等对象。
- device 需要 model-specific persistent state/trace/lanes：允许 custom scheduler/runner，但必须显式重建 vLLM request/KV/output transaction。
- lowering 以 functional/static IR 为中心：在模型前端做 functionalization，并把 shape/sharding 编入 compile key。

## 反模式

- 以“能 import plugin”替代 runtime compatibility。
- 在多个 patch 中复制 upstream private behavior，却没有 drift detector。
- 在 runner 静默关闭功能而不暴露 effective config。
- 用通用 `gpu_memory_utilization` 名称掩盖不同物理内存语义。
- 把单模型 generator/QPC 成功提升为 platform-wide feature support。

## 结论分类

- `SOURCE_IMPLEMENTED`：四类范式均来自本轮固定 revision 的实际入口与关键对象。
- `INFERENCE`：适配面越宽，升级和组合状态空间通常越大。
- `RECOMMENDATION`：先选最窄但能保持语义完整的接入范式；若替换 scheduler，必须提交事务等价性说明。
- `UNKNOWN`：四类 backend 在同一 workload/SLO 下的相对成本与性能。
