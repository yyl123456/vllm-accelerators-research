# 跨 Backend 风险、成本与维护矩阵

## 文档契约

- owner：长期维护、升级、验证与运维成本模型。
- 依赖输入：`74`、`84`–`86`、`100`–`135`。
- 唯一输出：风险预算和团队 ownership 决策。
- 不讨论：是否支持某功能或最终硬件选择；由 `141`、`144` 持有。

## 风险维度

| 风险 | Ascend | QAIC | TT | TPU |
|---|---|---|---|---|
| upstream API drift | 高：patch 面广 | 中：runner/mode API | 高：custom scheduler/engine | 中高：runner/config/patchers |
| runtime ABI tuple | CANN/TorchNPU/ACL/HCCL | SDK/firmware/QEfficient/QPC | firmware/tt-metal/TTNN/plugin | JAX/jaxlib/libtpu/TorchAX/Pathways |
| shape specialization | ACLGraph buckets | QPC profiles | model trace/buckets | JAX/XLA buckets |
| dynamic request impedance | 中 | AoT 高、eager 中 | 高但自有 scheduler 吸收 | 高，靠 padding/functionalization |
| multi-device complexity | HCCL/rank | PCIe/session/topology | mesh/fabric/lanes | SPMD/ICI/multi-host |
| evidence availability | vendor CI，需 provenance | SDK/硬件门槛高 | model/SKU 强绑定 | matrix 丰富，仍需 TPU provenance |

该表是架构风险分类，不是定量排名。没有团队规模、发布频率、设备访问和 SLA 数据时不能计算总拥有成本。

## 成本分解

```text
TCO_backend = bring-up + model-port + kernel/compiler tuning
            + compatibility CI + hardware lab
            + release qualification + on-call/recovery
            + upstream rebase/drift + capacity inefficiency
```

采购价格只是其中一项。若每次 vLLM 升级要重放大量 patches，或每个模型/shape 都要生成和管理专用 artifact，软件维护可能主导总成本。

## Ownership 最小集合

- upstream liaison：跟踪 vLLM private/public contract 漂移。
- runtime owner：维护 driver/firmware/compiler/package tuple。
- model/kernel owner：数值、layout、shape 与性能。
- serving owner：scheduler/KV/output/SLO 与故障恢复。
- release/evidence owner：manifest、CI provenance、回滚与审计。

一人可以兼任，但责任不能消失。跨层错误若没有唯一 owner，最终会在“模型、runtime、vLLM”之间循环转派。

## 风险压缩策略

1. 固定 known-good tuple，升级一层一次。
2. 用 contract/negative tests 检查未支持组合。
3. 将 patches 映射到 upstream symbols 和 removal plan。
4. 保存 compile/trace/QPC manifests 与 effective config。
5. 硬件 CI 分层：smoke、numeric、stress、performance，不相互冒充。

## 结论分类

- `INFERENCE`：表中风险来自源码适配面与架构耦合的比较。
- `RECOMMENDATION`：立项前先为五类 owner 和 hardware CI 预算，而不是只估算 kernel bring-up。
- `UNKNOWN`：各 backend 的实际人月、故障率、设备价格、能耗和 SLA 成本。
