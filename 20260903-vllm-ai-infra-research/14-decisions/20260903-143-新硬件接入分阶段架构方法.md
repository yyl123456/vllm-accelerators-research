# 新硬件接入分阶段架构方法

## 文档契约

- owner：从硬件研究到 vLLM backend 发布的阶段方法。
- 依赖输入：`70`–`95` 与四类 backend 案例。
- 唯一输出：每阶段输入、产物、退出条件和失败停止点。
- 不讨论：针对已有四平台的选择；由 `144` 持有。

## Phase 0：硬件/Runtime 事实表

产物：计算单元、memory hierarchy、DMA/queue/event、collective/topology、dtype、shape、compiler/runtime ABI 表。退出条件：能回答 physical completion 与 buffer reuse，而非只有峰值规格。

停止点：没有 completion、memory ownership 或多设备 identity API 时，先解决 runtime contract，不能直接写 vLLM adapter。

## Phase 1：最小 Platform 与单请求 Eager

产物：discovery、device identity、worker init/close、model load、单 prefill/decode、host sampling。退出条件：固定 tuple 下 device smoke 与小规模 numeric golden。

停止点：禁止用 CPU fallback 伪造设备 PASS；所有 fallback 必须可观测。

## Phase 2：KV 与动态 Batch 语义

产物：KV spec/layout/block table、request-row mapping、admission、abort/preempt、long context。退出条件：allocator/model/device completion 在同一 epoch，覆盖 row/block reuse。

## Phase 3：编译/Trace/Artifact

产物：specialization key、bucket/profile manifest、warmup、cache invalidation、miss/fallback policy。退出条件：cold/warm 可区分，wrong-key negative tests fail closed。

## Phase 4：分布式与高级功能

一次引入一个轴：TP→PP/DP→EP/CP，再逐个加入 prefix、offload/P-D、LoRA、MM、spec、grammar、device sampling。每项都需组合矩阵，不把单项测试相乘。

## Phase 5：生产与发布

产物：readiness levels、metrics/traces、fault taxonomy、rolling upgrade、rollback、capacity/perf envelope 和 signed tuple manifest。退出条件：device numeric、stress 和 performance artifacts 可追溯。

## 每阶段统一验收表

| 项 | 必答问题 |
|---|---|
| state | owner、epoch、create/commit/release 是谁 |
| data | logical/physical layout 与传输 |
| async | completion 如何证明可复用 |
| compile | key、guard、artifact、miss |
| failure | fail closed、cleanup、retry scope |
| evidence | 02 定义的事实来源类型 × 验证成熟度 |

## 架构评审门禁

任何阶段若修改 scheduler/output semantics，必须给出与 vLLM request state machine 的事务对应；若依赖 upstream private symbols，必须有 drift test；若需要 model-specific exception，必须进入 machine-readable capability，而不是散落 identity check。

## 结论

- `RECOMMENDATION`：按语义风险而非代码模块顺序推进；KV/async correctness 早于性能调优。
- `INFERENCE`：四类 backend 的失败经验共同指向 tuple、shape、state ownership 和 evidence provenance 四个核心治理对象。
- `UNKNOWN`：新硬件的阶段工期需在 Phase 0 后估算。
