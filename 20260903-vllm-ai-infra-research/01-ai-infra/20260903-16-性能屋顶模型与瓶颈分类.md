# 性能屋顶模型与瓶颈分类

## 本篇唯一主问题

如何用 compute、memory、interconnect、host 和 capacity 的上界分类 LLM 推理瓶颈，又为什么这些上界不能直接换算 tokens/s？

## In scope

arithmetic intensity、roofline、工作量/数据量账本、权重和 KV 流量、collective、host overhead、容量瓶颈、利用率与实验归因。

## Out of scope

不提供具体芯片的理论规格表，不声称某 backend 属于固定瓶颈，不以 roofline 替代 profiler 和 serving benchmark。

## 基本屋顶模型

对一段工作：

```text
Arithmetic Intensity I = useful operations / bytes moved
Attainable performance <= min(Peak compute, I * sustainable bandwidth)
```

这个模型要先回答“bytes 从哪里移到哪里”：HBM/LPDDR↔on-chip SRAM、SRAM↔register、host↔device、device↔device 是不同 roofline。使用厂商 peak FLOPS 与 HBM peak bandwidth 只能得到第一层上界，不包含 kernel 形状、存储效率、通信和 host scheduling。

## 工作量必须区分有效与实际

```text
useful work:   为最终 accepted outputs 所必需的数学运算
executed work: padding + recompute + rejected draft + fallback + redundant ranks
moved bytes:   weights + KV + activations + metadata + staging + collectives
```

高硬件利用率可以在执行大量 padding/rejected work 时出现。因此实验必须同时报告 device utilization 和 useful goodput。

## 五种主要瓶颈

### Compute throughput

表现：矩阵/向量单元长时间活跃，改变 batch/tile 后吞吐接近计算规格比例。

不能只看“占用率”：低精度矩阵单元可忙碌于 padding，或因 shape 不佳只达到很低的有效 FLOPS。

### Memory bandwidth/latency

表现：增加计算单元不提升性能，压缩 weight/KV 或增加 reuse 有效，性能随可持续 bandwidth 变化。decode 小 batch 常有该特征，长 context attention 则增加 KV 读取。

### Interconnect/collective

表现：扩展 device 后单请求或总 goodput 不再增长，collective 在 critical path，rank skew 导致其他设备等待。TP all-reduce、EP all-to-all、PP activation、KV transfer 需要分开计账。

### Host/control overhead

表现：device kernel 之间有 gap，CPU 线程/event loop 饱和，tokenization、batch packing、sampling、serialization 或 RPC 占主导。graph/trace replay、device sampling 和 async overlap 通常目标是该类瓶颈，但会引入 shape 与 completion 约束。

### Capacity/fragmentation

表现：compute 和 bandwidth 都未满，却因 KV、workspace、graph reservation、artifact slots 或 memory fragmentation 拒绝新请求。该瓶颈影响可行 concurrency，不一定直接表现为某个 kernel 慢。

## 权重流量的粗略上界

对参数量 `P` 的 dense 模型，若每次 decode iteration 必须从主存储读取大部分权重，权重字节近似 `P * b_w`。对 batch `B`，理想情况下同一次权重读取为 `B` 个 token 服务，因此增大 batch 可提高每字节有效运算。

但这个上界忽略：

- 权重是否分片，每 rank 只读一部分；
- on-chip cache/SRAM 复用和 layer pipeline；
- MoE 只激活 `k/E` 的 expert 但引入 routing/通信；
- quantization metadata/scales 和 unpack/dequant work；
- 不规则 shape、padding 和 kernel 效率；
- KV/activation/communication 与权重带宽竞争。

## KV 容量与带宽是两个问题

简化 dense attention 的每 token KV 字节约与：

```text
2 * N_l * N_kv * head_dim * b_kv
```

成正比。容量问题关注同时活着多少 token 状态；带宽问题关注每个 decode 步读取多少已有 KV。GQA/MQA、MLA、KV quant 可同时改变两者，sliding window 可限制读取/保留范围，prefix sharing 改变物理复制，但都需要结合具体 layout 计算。

## 为什么不能从规格页得到 tokens/s

```text
tokens/s != min(peak_FLOPS / theoretical_ops_per_token,
                peak_BW / theoretical_bytes_per_token)
```

缺失项包括：

- attainable 而非 peak compute/bandwidth；
- batch/shape/tile 效率和 padding；
- attention、sampling、normalization、routing 等非 GEMM 工作；
- launch/dispatch/compile/graph gap；
- collective、host-device copy、network output；
- request length 和 cache hit 分布；
- queueing、preemption 和 SLO 约束下不能使用的 batch；
- thermal/power/clock 和 runtime contention。

规格可用于提出假设和设计微基准，不是 serving result。

## 瓶颈归因的实验顺序

1. 固定 model/shape/dtype/backend/tuple，分开 prefill/decode。
2. 量出 wall time 和空转 gap，不先依赖单一 utilization 指标。
3. 变更 batch/tokens、context、quant、parallel size，观察 scaling curve。
4. 用 profiler 量取 compute、memory、collective、host 时间线，关联同一 batch/request。
5. 用微基准测 sustainable compute/bandwidth/collective，但不直接代替 end-to-end。
6. 对照工作量账本，解释有效 work 与 executed work 的差额。
7. 在真实 arrival/length/cache 分布下确认微观瓶颈是否仍决定 SLO/goodput。

## 架构决策点

1. 正在优化的是 useful work 还是 device executed work？
2. 哪一层数据搬运是瓶颈，测到的是 peak 还是 sustainable？
3. 增大 batch 提高效率时，是否破坏 TTFT/ITL SLO 或 KV headroom？
4. 增加设备后是 compute scaling 还是 collective/failure-domain 变大？
5. graph/trace 降低 host gap 的代价是多少 shape/profile/cache 复杂度？
6. 性能结论是否能用原始 trace 连接到 SLO/goodput？

## 证据边界

本篇公式是简化的 `INFERENCE/RECOMMENDATION` 分析工具。本研究不使用它们填充四类 backend 的 tokens/s；后者在无环境 tuple 和原始测量时均为 `UNKNOWN`。

## 本篇输出契约

硬件基础和 vendor 文档可使用五类瓶颈与实验顺序，但不再重写 roofline 定义或把理论上界写成性能。
