# 数值精度、量化与质量风险

## 本篇唯一主问题

一个后端在更换 dtype、量化格式、kernel、编译器或 sampling 位置后，如何判断“推理正确”，以及哪些质量风险不能用单次 token 对比发现？

## In scope

数值层次、dtype/累加精度、权重/激活/KV 量化、近似 kernel、随机采样、序列发散、模型评估与可重现性。

## Out of scope

不教学某种具体 quantization algorithm，不推荐 vendor 精度，不在无真实设备时声称数值通过。

## 正确性分层

| 层次 | 要回答的问题 | 不足的证据 |
|---|---|---|
| shape/type | 输入输出 shape、dtype、layout 是否合法 | 能 compile/run |
| operator | 单算子在代表 shape 上误差如何 | 一个 tiny tensor |
| layer/block | residual、norm、attention、MoE 组合后误差 | 各算子分别通过 |
| model logits | prefill/decode 的 logits/top-k/order 是否可接受 | 只比 argmax token |
| sequence | 长序列中误差是否改变采样路径 | 只比第一 token |
| task quality | perplexity/任务准确率/人评是否达门槛 | 少量样例“看起来正常” |
| service semantics | seed、logprob、stop、grammar、batch invariance 是否符合 API | 模型质量 eval |

后端接入必须先定义每层 acceptance，不能用一个 end-to-end prompt 替代所有层。

## 数值格式不只是一个 dtype 名称

同一个“FP8”或“INT8”声称还缺少：

- 权重、激活、KV、communication 分别使用什么格式；
- per-tensor/per-channel/per-group/per-token scale；
- symmetric/asymmetric、zero point、group size；
- scale 计算是 offline calibration 还是 online dynamic；
- accumulator 精度、约减顺序和 rounding mode；
- saturation、subnormal、NaN/Inf 行为；
- weight packing/layout 与 kernel/compiler ABI；
- 哪些敏感算子保留更高精度。

如果 scale/layout 不在 artifact key 中，同名量化可以错误复用 compiled artifact。

## KV 量化有时间维度

权重在服务运行前固定，KV 则在每个 token 生成。KV 量化的误差会：

- 被后续每一个 decode attention 反复读取；
- 随 context 增长累积不同位置和 head 的误差；
- 与 RoPE、sliding window、MLA/GQA 的 layout/scale 强耦合；
- 影响 prefix cache 和 KV transfer 的兼容性；
- 在 P/D 解耦时需要 producer/consumer 对 dtype/scale/layout 一致。

因此 KV quant 必须测长 context、多步 decode 和 cache transfer，不能只测一次 attention output。

## 浮点并行会改变结果

TP/EP/all-reduce/all-to-all 可改变加法顺序，fusion 可变更 rounding 点，compiler 可选择不同近似实现。由于浮点加法不具有数学上的结合律，bitwise equality 不总是合理门槛，但“不 bitwise”也不意味着任意误差都可接受。

验收应根据层次使用：

- absolute/relative error 和 ULP；
- cosine similarity 或 normalized error；
- logits top-k overlap、rank correlation、KL divergence；
- greedy exact-match rate；
- stochastic distribution test；
- perplexity/task metric delta；
- batch/topology invariance 或明确的非确定性契约。

## 采样使小 logits 误差放大成序列差异

当两个 token 概率接近，很小的 logits 改变就可以改变 top-k/order 或随机样本。一旦早期 token 分叉，后续 context 已不同，逐 token tensor 对比失去意义。

因此：

- greedy decode 可用 exact sequence rate 发现边界问题，但仍需 logits metric 解释临界 token；
- stochastic decode 应固定 RNG contract，或比较分布/任务质量，不强求不同 backend 生成字节相同；
- device sampling 和 host sampling 必须对 seed、counter advance、rejected/intermediate token 有明确协议；
- speculative decoding 必须保证 rejected token 不污染 target KV/RNG/output history。

## 精度验证矩阵

| 轴 | 至少覆盖 |
|---|---|
| phase | prefill、single-token decode、multi-token/spec verify |
| length | short、block boundary、long context、max supported |
| batch | single、mixed lengths、continuous add/remove |
| cache | miss、partial hit、full-block hit、evict/recompute |
| feature | quant、LoRA、grammar、logprob、MM、spec |
| topology | 1 device、TP/PP/EP 支持点 |
| control | preempt、abort、resume、prefix reset |
| output | logits、token、logprob、finish reason、RNG |

该矩阵不要做无条件笛卡尔积。应根据数据/状态相交点选 pairwise 和高风险组合，但 release claim 中的组合必须真正有测试覆盖。

## 架构决策点

1. 正确性门槛是 operator、logits、sequence 还是 task quality？
2. reference backend/revision/dtype 是什么，reference 自身有无非确定性？
3. weight/activation/KV/communication 的数值格式和 accumulator 分别是什么？
4. batch、topology、graph/eager 改变时，允许多大结果漂移？
5. sampling RNG 在 host/device/spec/preemption 路径上的推进规则是什么？
6. 数值失败是否能通过 metrics/NaN guard 及时发现，还是会静默生成？

## 证据边界

本篇给出 `RECOMMENDATION`层的验证方法。本次没有四类 vendor 硬件上的 logits/eval artifact，因此它们的数值正确性在本研究中为 `UNKNOWN`，即使存在单元测试或 README 支持声称。

## 本篇输出契约

后续 model、attention、sampling、compiler 和 vendor 文档只需映射自己的 numerical contract 和证据等级，不重写数值验证分层。
