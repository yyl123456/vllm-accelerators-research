# 多租户服务与资源隔离

## 本篇唯一主问题

多个租户共享模型、KV、缓存、计算和观测系统时，哪些资源必须隔离，哪些可安全共享？

## In scope

租户身份、配额、调度、缓存 namespace、LoRA/model locality、时序侧信道、metrics cardinality、计费和故障域。

## Out of scope

不解释具体鉴权协议，不审计 vLLM 安全漏洞，不将进程隔离自动等同于完整多租户安全。

## 租户身份必须穿过哪些层

```text
credential -> authenticated tenant
  -> quota/SLO class
  -> routing and replica eligibility
  -> queue/fairness accounting
  -> cache namespace and sharing policy
  -> model/adapter authorization
  -> metrics/logs/billing attribution
  -> deletion and incident scope
```

如果 tenant identity 只存在 gateway，engine 内只看 request ID，那么 engine 不能直接强制 tenant-level KV 配额或公平性。这不一定是错误：可以由外部 router 把租户分到独立 replica/pool。但架构必须明确 enforcement owner，不得同时假定外部和 engine 都会做。

## 资源隔离矩阵

| 资源 | 共享收益 | 主要风险 | 最小控制 |
|---|---|---|---|
| model weights | 最大的内存复用 | 未授权模型访问 | model ACL + replica eligibility |
| KV blocks | 降低长前缀重算 | prompt 内容/命中时序泄漏 | salted namespace + sharing policy |
| prefix hash index | 高效 lookup | hash collision、membership oracle | 完整身份、salt、租户边界 |
| LoRA/adapter cache | 避免重复加载 | 越权使用、驱逐干扰 | adapter ACL + per-tenant quota/locality |
| multimodal encoder cache | 复用图像/音频编码 | media hash 泄漏、内容跨租户复用 | content/tenant namespace + retention |
| compiler/graph cache | 降低 cold start | shape/model artifact 混淆 | immutable artifact key + provenance |
| batch | 提高设备效率 | timing/noisy-neighbor、fault blast radius | fairness + bounded batch residence |
| device memory | 提高利用率 | OOM 相互影响 | hard pool/quota/headroom |
| host CPU/network | 运维简单 | tokenizer/stream flood | cgroup/rate/concurrency limits |
| metrics/logs | 统一运维 | prompt/token/tenant 泄漏，cardinality DoS | redact、sample、label allowlist |

## Prefix cache 共享是安全决策

一个前缀命中可以泄漏：

- 某个具体 prompt 或文档是否近期被另一租户使用；
- 长度、模型或 adapter 的局部信息；
- 通过 TTFT 差异观测的 cache membership；
- 若 hash namespace 不包含 model/adapter/position/多模态语义，还可能导致错误复用。

所以共享策略至少有三级：

1. 每 request 独立：不做跨请求 prefix reuse；
2. 租户内共享：hash 与 namespace 包含租户身份；
3. 显式跨租户共享：仅用于公共、不敏感且版本锁定的前缀，由平台创建而非自动从用户 prompt 推断。

加 salt 能改变 hash namespace，但不自动解决时序、配额和 retention 问题。

## LoRA 和 model locality 是路由问题

当 replica 只缓存部分 adapter，router 需要知道：

- 租户是否有权使用 adapter；
- adapter revision 是否与 base model 兼容；
- 目标 replica 是否已 warm，若 miss 则加载耗时和驱逐影响；
- 一个租户是否可用高 cardinality adapter 污染所有 replica cache；
- 加载失败是 request-level 错误还是 replica 健康问题。

adapter miss 可以在 request SLO 内同步加载，也可以先拒绝/预热。这是产品契约，不能由实现偶然决定。

## Noisy neighbor 的四种形式

### 容量占用

长上下文租户占据 KV，使其他租户无法 admission，即使 compute utilization 不高。

### 计算干扰

长 prefill、大 multimodal encoder 或低效 shape 阻塞交互 decode，放大 ITL tail。

### 控制面攻击

大量无效 request、grammar compile、adapter miss、metrics label 或断开重试耗尽 CPU/event-loop/cache。

### 故障放大

一个租户触发 OOM、compiler bug 或 device assert，使共享 worker/process group 内所有请求失败。

## 配额不应只是 request/s

有用的租户配额向量可包含：

```text
concurrent requests
queued requests and bytes
input/output tokens per time window
live KV blocks or context-token-seconds
LoRA/model/MM cache footprint
compile/profile creation rate
stream connections and output bytes
priority/SLO class budget
```

`context-token-seconds` 这类单位能表达“一个长 context 占用多久”，比只计 output token 更贴近 KV 资源，但它仍不能替代 device-time 或通信计费。

## 计费与调度计账不必相同

- 产品可按 input/output token 计费，因为用户易理解。
- scheduler 可按 scheduled token/KV block 运行，因为这是它可观测的资源。
- 容量规划需要 device time、memory bandwidth、KV residence 和 cache miss 更完整的成本。
- speculative rejected token、padding、recompute 会消耗资源却不应伪装成用户 output token。

若用同一单位同时做 billing、fairness 和 capacity，需要证明它与三类目标的误差可接受。

## 架构决策点

1. tenant identity 在哪一层被丢弃，丢弃后哪个 enforcement 不再可能？
2. prefix/MM/LoRA cache 的 namespace 是 request、tenant、organization 还是全局？
3. batch 中混合租户是否符合安全和故障域要求？
4. 配额限制了 request rate，还是真正的 KV/cache/compile/stream 资源？
5. adapter/model miss 属于 request latency 还是平台预热责任？
6. metrics/logs 会不会泄漏 prompt、token、adapter 或租户活动？
7. 单租户能否通过 OOM/compiler fault 击穿共享 replica？

## 证据边界

这是 `RECOMMENDATION`层的隔离模型。它不声称 vLLM 当前内建了完整租户 identity/quota/cache isolation。实际 endpoint/plugin/security 边界由 `08-production/85` 以源码和官方文档审计。
