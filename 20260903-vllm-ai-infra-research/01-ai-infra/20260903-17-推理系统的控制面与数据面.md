# 推理系统的控制面与数据面

## 本篇唯一主问题

推理系统中哪些工作属于控制面、数据面和管理面，三者如何通过版本化契约协作？

## In scope

平面分离、责任、时间尺度、配置/状态发布、资源视图、故障反馈和异构 backend 编排。

## Out of scope

不指定 Kubernetes/Ray 部署实现，不把 vLLM 某个 class 简单标记为整个平面，不讨论 kernel 细节。

## 三个平面

### 管理面 Management plane

时间尺度从分钟到数天，负责：

- 模型、adapter、tokenizer、container、plugin 和 compiler artifact 的发布；
- driver/firmware/runtime 版本与 hardware SKU/topology inventory；
- deployment、rollout、rollback、capacity pool 和 tenant policy；
- 长期性能/质量/成本基线和变更审核；
- artifact provenance、签名、SBOM 和保留策略。

### 控制面 Control plane

时间尺度从毫秒到分钟，负责：

- request authentication context、routing、admission、priority 和 cancellation；
- replica/model/backend eligibility 和健康视图；
- scheduler 产生 iteration/batch plan；
- logical KV/resource allocation、preemption 和 progress bookkeeping；
- fault classification、retry decision、load shedding 和 autoscaling signal；
- 将 SLO 与资源限制转换为动作。

### 数据面 Data plane

时间尺度从微秒到秒，负责：

- token/media tensor 处理、batch packing 和 physical buffer mapping；
- model forward、attention/KV read-write、sampling 和 collective；
- host-device/device-device/KV transfer；
- graph/trace/executable 调用和 runtime completion；
- 返回 tensor/token/error/event 给控制面。

## 分类不等于进程分离

一个 EngineCore 进程可同时执行控制面调度和通过 executor 发起数据面工作；worker 可持有控制类的 model/buffer state；runtime compiler 可在请求路径中触发管理类 artifact creation。平面分离的价值是定义决策与执行契约，不是强迫每类工作有独立微服务。

## 控制面到数据面的最小协议

```text
WorkDescriptor {
  request/version identities
  token ranges and positions
  input/batch slot mapping
  logical-to-physical KV mapping
  model/adapter/artifact identity
  sampling/spec/grammar parameters
  parallel rank/group/topology context
  deadline/cancel generation or epoch
  expected output and completion semantics
}

WorkResult {
  descriptor identity and sequence
  produced/accepted tokens or tensors
  state deltas and KV visibility
  completion level
  per-work errors and device/runtime faults
  measurements needed for attribution
}
```

vLLM 当前不一定存在一个包含所有字段的 public struct；这是 `RECOMMENDATION`层的契约核对表。后续 `SchedulerOutput`、runner input、connector metadata 和 vendor descriptor 分析会显示这些语义在何处分散。

## 配置必须区分 desired、effective 和 observed

- **desired**：用户/部署希望开启的功能与参数。
- **effective**：platform/plugin/runtime 校验和修正后真正使用的配置。
- **observed**：运行时实际选到的 kernel、graph/profile、fallback、topology 和容量。

若只保存 desired CLI，一个 backend 可以静默关闭 chunked prefill/async/graph，而运维仍认为功能已开启。effective config 应可记录，observed mode 应可通过 metrics/trace 验证。

## 异构 backend 不应共享一个虚假容量数字

不同 backend 可以共享 API 和业务 SLO，但其 capacity descriptor 至少需表达：

- model/quant/feature eligibility；
- context/batch/profile/shape 可行域；
- KV 容量和增长风险；
- prefill/decode 成本估计与当前 queue；
- topology/parallelism 和 failure domain；
- artifact warmness 和是否可 fallback；
- observed health、error 和 SLO headroom。

路由器可以用共同的抽象字段，但不应把“空闲 device count”当作可比容量。

## 快慢反馈环

```text
microseconds-milliseconds:
  runtime completion, stream/event, kernel error

milliseconds-seconds:
  scheduler batch result, queue/KV pressure, request SLO prediction

seconds-minutes:
  replica health, load shedding, routing weights, autoscaling

minutes-days:
  rollout, artifact invalidation, capacity purchase, model/quality policy
```

快环不应同步等待慢环决策。例如设备报错后，worker 必须先停止不安全的 buffer reuse，不能等 autoscaler 判定；management plane 又不应根据一次短暂 queue spike 立即改变 firmware/image。

## 接口版本化

三类边界需要不同版本：

1. **request protocol version**：API 字段、stream chunk、error semantics；
2. **engine internal contract**：SchedulerOutput、runner input/output、connector metadata；
3. **artifact/release tuple**：model weights/layout、compiled executable、runtime/driver/firmware/SKU。

只固定 Python package 版本不能保证后两类契约。OOT plugin 尤其需要在 CI 中将 upstream internal API 变化与真实 feature matrix 关联。

## 架构决策点

1. model placement、routing、admission、iteration scheduling 分别是谁的决策？
2. 数据面返回的 completion/error 是否足以让控制面安全回收？
3. desired/effective/observed config 是否都可审计？
4. 异构 router 的 eligibility/capacity 是否包含 feature、shape、tuple 和 failure domain？
5. 快环故障能否在本地 fail closed，而不依赖慢环？
6. internal contract 漂移时，是否有机器可检测的版本/兼容性门禁？

## 证据边界

三平面和 descriptor 是 `RECOMMENDATION`层的架构模型。当前 vLLM 与各 plugin 对这些责任的具体切分，由后续固定 revision 文档标为 `SOURCE_IMPLEMENTED`。

## 本篇输出契约

后续 vLLM、production 和 vendor 文档可将组件映射到 management/control/data plane，但不重写三平面定义。
