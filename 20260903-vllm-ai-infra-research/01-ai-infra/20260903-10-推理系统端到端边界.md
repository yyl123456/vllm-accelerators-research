# 推理系统端到端边界

## 本篇唯一主问题

一个在线 LLM 请求从客户端到加速器再回到客户端，哪些层属于端到端推理系统，各层交换什么？

## In scope

边界、层次、输入/输出契约、横跨层次的 request identity、deadline、cancellation、resource accounting 和 observability context。

## Out of scope

不讨论某个 scheduler 算法、KV 物理布局、kernel 实现或 vendor 设备规格。

## 系统边界不是 vLLM 进程边界

生产推理系统通常至少包含：

```text
client / agent framework
  ↓ request, auth, deadline, idempotency key
gateway / API protocol / tenant policy
  ↓ normalized inference request, cancellation, trace context
router / admission / model placement
  ↓ selected replica, queue ownership
serving engine frontend
  ↓ engine request
scheduler / KV coordinator / execution control
  ↓ batch plan, logical resource assignment
executor / worker / model runner
  ↓ device buffers, programs, collectives
runtime / compiler / driver / firmware
  ↓ commands, DMA, events
accelerator / memory / fabric
  ↑ completion, tensors, counters, faults
sampler / output processor / tokenizer
  ↑ token IDs, logprobs, finish reason
streaming protocol / gateway / client
```

vLLM 覆盖其中很多层，但它不自动拥有全局租户配额、跨集群路由、硬件供应、电力预算、跨地域容灾或客户端重试语义。把“使用 vLLM”等同于完整推理平台，会留下无 owner 的故障和 SLO 边界。

## 各层最小契约

| 层 | 主要输入 | 主要输出 | 不能丢失的语义 |
|---|---|---|---|
| Client | prompt/messages/media/tools | request + deadline | 用户意图、取消、重试身份 |
| Gateway | protocol request + identity | authenticated normalized request | tenant、quota、trace、deadline |
| Router | model/SLO/resource view | selected replica or rejection | placement reason、queue owner |
| Engine frontend | normalized request | engine-core request | tokenization/template/sampling semantics |
| Scheduler | request state + resource state | iteration/batch plan | fairness、progress、logical KV ownership |
| Executor/runner | batch plan + physical resources | model output/future | rank mapping、buffer lifetime、completion |
| Runtime/device | program + buffers | tensor/event/error | ordering、visibility、fault identity |
| Output path | token/logprob/status | stream chunks/final response | ordering、exactly-once publication、finish reason |

“最小”不意味着这些契约已被所有实现形式化。它是架构审查时需要追踪的语义。

## 六条横跨全栈的控制链

### 1. Request identity

request ID 必须足以区分重试、parallel sampling 子请求、streaming session 更新和内部 batch slot。如果 gateway ID、engine ID 和 worker-local index 被当作同一 namespace，slot reuse 可能导致 metrics 误归因或取消错请求。

### 2. Deadline and SLO budget

外部 deadline 不应只在 HTTP 层生效。它需被拆成 queue budget、prefill budget、first-token budget、per-token cadence 和 stream delivery budget。内核不一定支持 deadline-aware scheduling，但路由和 admission 必须知道请求是否已不可能达标。

### 3. Cancellation

客户端断开只是 cancellation trigger，不是 device work 已停止的证据。完整链路应区分：

1. 不再向客户端写数据；
2. 不再调度新 token work；
3. 标记已提交 work 的输出为 stale；
4. 等待会写入共享 buffer/KV 的 work 达到安全 completion；
5. 回收逻辑和物理资源；
6. 向 metrics/billing 记录终止原因。

### 4. Resource accounting

请求不只消耗 token budget，还消耗 KV pages、activation/workspace、input slots、compiler/graph cache、communication buffer、host-pinned memory、network bandwidth 和 stream connections。不同资源的 owner 必须对同一 request 有可关联的 accounting key。

### 5. Failure identity

“推理失败”至少要区分 protocol validation、queue timeout、model unsupported、compile error、OOM、collective timeout、device reset、worker loss、output stream failure。如果全部折叠为 HTTP 500，系统无法选择安全重试、路由转移或容量降级。

### 6. Observability context

同一 request 应能关联 gateway span、queue event、scheduler iteration、batch ID、worker/rank、compile/cache event、device profile 和 stream write。如果只有 request-level 总延迟和 device-level kernel trace，两者无关联 ID，就不能从 trace 解释尾延迟。

## 端到端线性化点

系统需要对外部可观测事件定义线性化点：

| 事件 | 候选线性化点 | 典型风险 |
|---|---|---|
| accepted | admission 接管请求 | HTTP 已接收但内部已拒绝 |
| first token | 首个 token 可向 stream 公布 | device 计算完成不等于客户端收到 |
| token committed | 输出历史和 KV/RNG 状态一致更新 | spec reject 或 retry 重复公布 |
| finished | finish reason 与最终 chunk 已排队写出 | connection failure 遮蔽计算完成 |
| cancelled | 不再有外部输出且内部资源进入可回收状态 | 只取消 frontend task，device 继续写 |

不同 API 可以选择不同 accepted/finished 语义，但不可以在无文档的情况下依赖运气。

## 分层故障不能只用重试处理

- 在任何 token 公布前，若 request 是确定性且状态未外泄，可能安全重试。
- 公布部分 token 后，在另一 replica 重放可能因 RNG、浮点、backend 或 batch 差异产生分叉。
- 在共享 prefix/remote KV 上的故障可能污染后续请求，不能只失败当前 request。
- collective 中某 rank 失败通常是 process-group 故障，不是单请求故障。
- compiler artifact 错误可能是 fleet-wide 确定性错误，无限重试只会放大负载。

## 架构决策点

1. 系统的真正 admission owner 在 gateway/router 还是 engine？两层都可拒绝时如何避免重复排队？
2. deadline 是软目标还是超时后必须终止计算的硬契约？
3. streaming 部分输出后，系统允许自动重试吗？如何避免重复 token？
4. resource accounting 是否覆盖 KV 之外的 graph/cache/communication/host memory？
5. 故障是 request、worker、rank group、replica、node 还是 artifact 级？谁有权重建？
6. observability context 是否跨过了会丢失 Python contextvar 的进程/RPC/device 边界？
