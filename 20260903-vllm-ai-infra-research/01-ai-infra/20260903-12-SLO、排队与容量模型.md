# SLO、排队与容量模型

## 本篇唯一主问题

如何把 LLM 服务的用户体验转换为可测量 SLO，并用排队与容量模型判断系统是否有可行的负载区间？

## In scope

TTFT、TPOT/ITL、E2E latency、throughput、goodput、availability、queueing delay、service demand、utilization、tail latency、Little's Law 和容量安全边界。

## Out of scope

不定义具体 admission/fairness 算法，不提供 vendor 性能数字，不把简化排队公式当作真实加速器的精确仿真。

## 指标边界

### TTFT

`Time To First Token` 通常从服务接收请求到首个输出 token 可见。但必须明确起止点：

- client 开始发送还是 server 读完 body；
- 首 token 在 device 产生、host detokenize、SSE chunk 写入 socket，还是 client 收到；
- tokenize、template、image fetch/encode、queueing、compile 和 prefix-cache lookup 是否计入。

平台 SLO 宜使用客户可观测边界；engine 内部还需分解 TTFT 以定位瓶颈。

### TPOT/ITL

`Time Per Output Token` 可表示 decode 总时间除以 token 数；`Inter-Token Latency` 是相邻可见 token 之间的分布。均值 TPOT 可以隐藏长 prefill 导致的周期性 stall，所以 streaming 体验应关注 ITL 的 p95/p99 或最大连续停顿。

### E2E latency

从请求开始到最终 finish 的时间。它受输出长度强烈影响，因此比较时必须固定或分层 `L_o`。

### Throughput

至少有三种不可混用的定义：

- request/s：受长度分布影响；
- input/output/total token/s：对 prefill/decode 权重不同；
- accepted/committed token/s：speculative decoding 中要排除被拒绝 draft token。

### Goodput

goodput 只计入满足定义 SLO 的请求或 token。它阻止系统通过把 utilization 推到极限、同时让大量请求超时来夸大 throughput。DistServe 使用 TTFT/TPOT 约束下的可服务请求率这类思路。[论文](https://arxiv.org/abs/2401.09670)

## 延迟分解

对一个请求，可用以下账本而不是单一计时器：

```text
T_e2e = T_ingress
      + T_auth_route
      + T_queue
      + T_tokenize_or_mm
      + T_compile_warmup_if_any
      + T_prefill
      + T_first_sample_and_emit
      + sum(T_decode_iteration + T_emit_gap)
      + T_finalize
```

这是 accounting identity，不表示各项一定串行。例如 host preparation 可与 device execution 重叠，multimodal encoder 可与其他请求 decode 并行／stream write 可由独立 event loop 处理。重叠时不能直接把 profiler 各 category 时间相加。

## Little's Law 只是一致性检查

在稳态、边界一致的系统中：

```text
N = λ W
```

`N` 是系统内平均请求数，`λ` 是完成率，`W` 是平均停留时间。它可用于检查 metrics 是否自洽，不能单独预测 p99，原因包括：

- LLM service time 受 `(L_p,L_o)` 影响，可呈 heavy tail；
- dynamic batching 使一个请求的 service rate 依赖其他请求；
- prefix cache、compile cache、LoRA locality 使 service time 非独立同分布；
- preemption 和 priority 使 waiting time 不是简单 FCFS 队列；
- 爆发流量使短时窗不处于稳态。

## Utilization 与 tail latency

当负载接近系统的有效服务率时，小幅 workload 波动就可导致 queue 大幅增长。LLM 还有多重“利用率”：

- compute unit occupancy；
- HBM/LPDDR bandwidth utilization；
- KV capacity utilization；
- graph/profile slot utilization；
- interconnect utilization；
- request concurrency/queue occupancy。

把 device utilization 保持 100% 不是 SLO-safe 目标。如果 KV 已满或长 prefill 使 ITL 尖峰，计算单元忙碌可以与 goodput 下降同时发生。

## 容量是多维可行域

简化的单数字“容量”会忽略以下约束：

```text
compute budget       >= scheduled compute work
memory bandwidth     >= weight + KV + activation traffic
KV capacity          >= live logical/physical state + safety margin
workspace            >= max concurrent kernels/graphs/collectives
interconnect         >= collective + KV transfer traffic
host capacity        >= tokenize + schedule + pack + sample + stream
compile/profile slots cover admitted shapes/modes
all selected points satisfy latency/error SLO
```

因此容量是 workload mix、调度参数、缓存状态、拓扑和 SLO 给定时的可行域。请求率只是其中一个坐标。

## 容量规划的三个边界

### Saturation boundary

持续 backlog 开始增长、吞吐不再线性增加的点。这个点可以高于 SLO-safe boundary。

### SLO-safe boundary

在给定 workload 和观测窗口中，同时满足 TTFT、ITL/TPOT、error rate 等分位数目标的最大输入负载。

### Operational boundary

在 SLO-safe 边界之下再预留 burst、replica loss、rolling upgrade、cache cold start 和测量误差后的运行点。它才是 autoscaling 和采购通常应使用的容量。

## 应当分层的 SLO

| 类型 | 典型关注 | 不应混为一条队列的原因 |
|---|---|---|
| 交互 chat | TTFT + ITL tail | 用户感知停顿，输出长度不确定 |
| batch generation | deadline + cost/throughput | 可容忍排队，追求资源效率 |
| agent/tool loop | TTFT + request chain completion | 一次延迟会乘上多轮调用 |
| coding/long context | long-prefill TTFT + decode cadence | KV 和 prefill 峰值大 |
| embeddings/rerank | request/batch latency | 没有自回归 ITL |
| multimodal | media preprocessing + TTFT | encoder 和 decoder 有不同瓶颈 |

## 架构决策点

1. SLO 的计时边界在 client、gateway 还是 engine？
2. 目标是吞吐、goodput、单用户延迟还是每成功请求成本？
3. 容量模型是否保留 workload class 和 cache state，还是错误地只用 tokens/s？
4. operational headroom 是否包含 replica loss、upgrade 和 cold compile？
5. autoscaler 使用 queue、KV pressure、TTFT prediction 还是 device utilization？指标是否领先于 SLO 失败？

## 证据边界

这里的延迟账本和容量多维模型是 `RECOMMENDATION`。Little's Law 是排队论一致性关系，但不是 vLLM 尾延迟预测器。任何具体容量值必须由指定 tuple 的 `EXPERIMENT_RESULT × PERFORMANCE_MEASURED` 数据给出。

## 本篇输出契约

admission、benchmark、capacity planning 和 autoscaling 文档使用本篇定义的指标边界和三类容量边界，不再重新定义 TTFT/TPOT/goodput。
