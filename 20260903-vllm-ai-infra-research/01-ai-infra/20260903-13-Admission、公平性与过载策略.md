# Admission、公平性与过载策略

## 本篇唯一主问题

当 LLM 服务不能同时满足所有请求时，应根据哪些资源和 SLO 做 admission，如何定义公平性并控制过载？

## In scope

admit/queue/reject/defer/preempt/route/degrade 决策，多维资源预估，FCFS/priority/deadline/tenant fairness，长短请求干扰，load shedding 和 backpressure。

## Out of scope

不解释 vLLM `Scheduler.schedule()` 的实现，不定义 autoscaling 机制，不解释多租户安全隔离。

## Admission 与 scheduling 不是同一问题

- **Admission** 决定系统是否接管一个新请求或新工作单元。
- **Scheduling** 决定已接管工作中哪些在当前 iteration 获得资源。
- **Routing** 决定由哪个 replica/pool 接管。
- **Autoscaling** 改变未来可用容量，通常比 iteration scheduling 慢多个时间尺度。

系统可以在 gateway 做粗粒度 admission，再在 engine 按 KV/token 做细粒度 scheduling。但若两层都维护无上限队列，请求会经历两次不可见排队，使 deadline 和 backpressure 失效。

## Admission 所需的请求信息

| 信息 | 是否可在入口精确知道 | 错估的影响 |
|---|---|---|
| prompt tokens | tokenization 后可知 | TTFT、prefill work、初始 KV |
| max output tokens | 可知上限 | 过度保守会降低容量 |
| actual output tokens | 不可预知 | decode 服务时间和 KV 增长不确定 |
| prefix-cache hit | lookup 后部分可知 | 命中会减少 work，但仍有 block alignment/last-token 语义 |
| speculative acceptance | 不可预知 | draft/verify 成本与收益不确定 |
| grammar/logprob cost | 可分类，难精确 | host/device sampling 和输出带宽 |
| multimodal encoder work | 可从媒体 shape 预估 | encoder memory/time/cache |
| LoRA/model locality | 需要 replica cache 视图 | 错路由导致 load/evict stall |
| deadline/priority/tenant | 来自业务契约 | 错误地犲牲高优先级 SLO |

因为实际输出长度不可预知，admission 是风险决策，而非精确 bin packing。

## 多维资源账本

一个候选请求的资源向量可抽象为：

```text
r = (
  prefill_compute,
  expected_decode_compute,
  KV_initial,
  KV_growth_risk,
  activation_workspace,
  graph_or_profile_slot,
  communication,
  host_work,
  output_bandwidth
)
```

实现可以使用更粗的 token/block budget，但架构师必须知道哪些维度被折叠。对静态图/AoT 后端，`graph_or_profile_slot` 可能比 token budget 更硬；对长上下文服务，KV 增长风险可能先于 compute 饱和。

## 公平性必须先定义主体和单位

“公平”可能指：

- 每个 request 获得相似的等待顺序；
- 每个 tenant 获得按权重分配的 token/device time；
- 每个 SLO class 达到约定 goodput；
- 长短请求都不被饿饿；
- 每个 replica/backend 不被路由不均压垮。

FCFS 只定义到达次序，它不保证资源公平：一个超长 prompt 可以阻塞大量交互请求。纯 shortest-job-first 可以降低平均延迟，但长任务可能饿饿，且 actual `L_o` 不可预知。

## 调度粒度与公平性

对多 iteration request，可以在不同粒度计账：

- **request-level**：一旦开始就持续服务到结束，延迟稳定但新请求易饿饿；
- **iteration-level**：每次可重组 batch，灵活但需追踪长期 progress；
- **token-level**：用 scheduled/computed/output token 计账，prefill token 和 decode token 成本不同；
- **device-time estimate**：理论上更贴近资源，但 batch 协同和 cache 使单请求成本难隔离；
- **dominant-resource share**：考虑 KV、compute、communication 中的主导占比，但需更复杂的估计和 enforcement。

“按 token 公平”对异构硬件尤其危险：某个 backend 可能要求纯 prefill/decode batch，某个 AoT profile 中 padding 成本远大于有效 token 数。

## 过载时可用的动作

| 动作 | 优点 | 风险/必要条件 |
|---|---|---|
| reject early | 不浪费排队和 device work | 要有可解释错误与 retry-after |
| bounded queue | 吸收短 burst | 队列必须 deadline-aware 并可观测 |
| route elsewhere | 使用其他容量 | 需要 model/feature/tenant/cache 兼容 |
| preempt | 为更高价值工作腾资源 | 重建成本、KV 和 in-flight completion 安全 |
| reduce max tokens | 有界化未来 KV/decode 风险 | 改变用户契约，需明示 |
| disable expensive features | 减少 logprob/beam/spec/mm 成本 | 不能静默改变语义 |
| shed low-priority tenants | 保护核心 SLO | 需要组织层面的公平契约 |
| scale out | 增加未来容量 | 冷启动、权重、compile 和 cache warmup 滞后 |

所有 degradation 都必须区分“拒绝一个特性”和“静默改变结果”。例如无法提供 logprobs 时显式拒绝比返回不完整数据更安全。

## Backpressure 必须向上游传播

一个健康的过载链路是：

```text
device/KV/compile pressure
  → engine exposes bounded capacity signal
  → router reduces assignments or chooses compatible replica
  → gateway bounds queue and returns retryable/non-retryable response
  → client applies bounded retry with jitter or degrades intentionally
```

如果压力只体现为 engine 内队列变长，上游会继续发送，直到 timeout storm、重试放大和 OOM。如果 autoscaler 只看 device utilization，又可能在 KV-full 但 compute 未满时错过过载。

## 负载估计错误时的安全性

admission estimator 必须定义估计偏差的处置：

- output 比预期更长：保留 KV safety margin，或显式 preempt/reject continuation；
- cache hit 未发生：不能让已 admission 的 request 突破硬内存上限；
- compile/profile miss：不得在高优先级队列中无限阻塞其他 shape；
- LoRA/model miss：加载工作应与已经就绪的请求隔离；
- worker/replica loss：剩余 operational headroom 应能吸收或快速拒绝，不是全部重排无界队列。

## 架构决策点

1. 是否只有一个可观测、有界的长期 queue owner？
2. admission 使用 token、KV、device time、profile slot 还是多维账本？
3. fairness 的主体是 request、tenant、SLO class 还是 device time？
4. 长 prompt、长 output、低 cache locality 请求是否能饿饿其他工作？
5. 优先级是否能跨 gateway、router 和 engine 传播，还是只改变一层队列？
6. degradation 是否明示给客户端，是否会改变模型语义？
7. 重试是否受 retry budget 约束，避免过载放大？

## 证据边界

本篇是 `RECOMMENDATION`层的 policy 模型。当代 vLLM 具体实现了哪些 token/block/priority/preemption 机制，由 `02-vllm-control/24-26` 以 `SOURCE_IMPLEMENTED` 证据回答；不能倒过来用这个理想模型声称 vLLM 已有全局 admission controller。

## 本篇输出契约

后续 scheduler、capacity 和 production 文档可使用本篇定义的 admission/scheduling/routing/autoscaling 边界与过载动作，不再重写 policy 分类。
