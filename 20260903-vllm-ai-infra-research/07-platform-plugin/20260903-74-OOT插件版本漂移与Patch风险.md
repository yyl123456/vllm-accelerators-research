# OOT 插件版本漂移与 Patch 风险

## 文档契约

- **唯一问题**：上游vLLM快速变化时，OOT插件怎样证明兼容并管理patch/fork负债。
- **In scope**：version pin、API/behavior drift、patch inventory、CI matrix、release ownership。
- **Out of scope**：单个vendor patch清单（105/116/126/135）、通用rolling release（86）。
- **证据基线**：当前六仓固定SHAs及各自packaging/patch目录。

漂移分为：import/signature drift、config schema drift、state/behavior drift、binary ABI drift和performance drift。前两类易在启动暴露；后几类可能“能跑”但abort、KV、sampling或artifact语义已错。

插件采用版本范围、pin exact commit、vendored patch或fork。宽范围降低安装冲突却增加未测组合；exact pin可复现但升级慢；runtime monkey patch最难审计；长期fork会漏安全/架构变化。

必须维护patch ledger：目标upstream SHA/file/hunk、目的、owner、依赖、是否已上游、删除条件、测试。每次rebase进行semantic diff，不能只靠patch clean apply。覆盖父方法时检查新默认行为和新增call sites。

release matrix固定vLLM/plugin/framework/runtime/driver/firmware/model/parallel/features；CI至少有import/config/source tests，真正supported claim还需device E2E/numeric/failure/perf。上游main smoke不能替代release branch。

架构门禁：P0 correctness/security patch无证据不发布；unsupported组合fail closed；patch数量/age和override surface作为债务指标。**结论**：OOT不是一次接入，而是持续承担上游协议演化。

## 漂移检测流水线

1. 比较 public/private symbols、Platform defaults 与 signatures。
2. 运行 imports、config 与 negative guards host tests。
3. 对每个 override 做 parent-call reachability/semantic diff。
4. 固定设备跑 smoke/numeric/abort/feature combinations。
5. 与上一 release 比较 performance/memory envelope。

patch ledger 必须记录 upstream SHA、版本区间、冲突策略与 removal condition；clean apply 只证明文本。`SOURCE_IMPLEMENTED`：六仓 patch/override 可静态核查；`RECOMMENDATION`：兼容区间只覆盖 CI tuple；`UNKNOWN`：无 device provenance 的范围不升级为 release support。
