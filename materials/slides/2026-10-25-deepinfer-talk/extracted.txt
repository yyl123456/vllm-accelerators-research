===== PAGE 11 / 32 =====
V4.1 的两种 KV 分开存
Block KV （ CSA ） SWA KV
内容 top-k + 压缩后的 KV 最近 128 个 token 的滑动窗口
显存分配按 128 个 token （压缩前）分页， 每个请求一张 block table 每个请求一个固定槽位（ StateBlock ）
持久化 3FS 本机内存， 只在 128 的整数倍位置存快照
跨机命中任何机器直接读 Entrypoint 记录快照在哪台机器， 走 400G VLAN 拉回来

===== PAGE 12 / 32 =====
SWA 槽位启动时静态预留， 不和 block KV 互相挪用
槽内按 pos % 134 当环形 buffer 用， 多出来的 6 个位置给 MTP 投机失败回退
启动时按 max_num_seqs × 1.2 预留槽位， 剩下的显存才给 block KV
调度时两边都分配得到才放行
每个请求的 SWA 快照约 1.4 MB （ 20 层 × 134 × 528 B ）

===== PAGE 15 / 32 =====
换入有四种搬法， 区别在固定开销和会不会影响前向调度
1. Copy engine 逐个拷： 每块调一次 cudaMemcpyAsync ， 每次是一个独立的 DMA 操作， 不占 SM
2. Copy engine 批量拷： cudaMemcpyBatchAsync（ CUDA 12.8 之后） ，一次调用交一批拷贝给 copy
engine ， 不占 SM ， 但 batch 大小要控制， CPU 提交也有开销
3. SM gather： 写个 kernel 用 SM 直接读 host 内存写到显存， 要占 SM ， 而且和前向 kernel 在同一个 GPU 队
列里
4. GDR：网卡做 RDMA write ， 从 shm 直接写到显存， 不占 SM ， 换入线程也不调 CUDA API
前三种都要过 CUDA ， 第四种完全绕开 CUDA 。 DeepSeek 选的是 GDR 。
Block KV 一个 block 一层是 22,784 B ， 命中 64K token 就是 512 个 block ， 源和目的地址都是散的。

EPLB 的目标： 降低每一步最慢那张卡的负载
核心是削峰， 不追求平均： 每一步整个系统的速度取决于那一步最慢的卡
在给定 worker 和专家槽位下， 让观测窗口里每一步 " 最慢那张卡 " 的总耗时最小

===== PAGE 22 / 32 =====
第一步： 冗余名额一个个分给最热的专家
过热的专家放哪张卡都扛不住， 只能复制。 每轮给一个专家加一份副本， 直到冗余名额用完， 每层单独算
每份负载 = 专家负载 ÷ 副本数。 对窗口里的每一步， 找出这一步每份负载最高的专家
假设这份副本给专家 j ： j 是某一步最热的， 那一步的最高负载就降下来； 不是的话， 那一步不变
把各步的最高负载加起来， 选加完后总和最小的 j
负载加上 1e-4 × 编号， 只是为了让各专家的值互不相同， argmax 结果确定

===== PAGE 25 / 32 =====
解决 EPLB 后， 剩下的是 DP 之间的均衡 （ DPLB ）
Prefill 和 decode 都是 DP + EP ， 每一层都要等 attention 算得最慢的那张卡， 大家再一起进 MoE 的 all-to-all
Prefill 和 decode 的 attention 耗时由不同因素决定， 表面上是两个 load balancer ， 实际都围绕 DPLB
DeepSeek 自评： 吞吐达到完全均衡时离线 benchmark 的 80%

Prefill ： 按上下文长度分 4 个桶
<16K 、 16–64K 、 64–256K 、 ≥ 256K
分桶的原因： attention 和上下文长度不是线性关系， 同样 1K token ， 500K 上下文的比 10K 的慢； 不同长度
下 attention 和 MoE 的比例不同
所有机器共享 3FS ， 上下文增长时请求在桶之间迁移， 不降低命中率
引擎也会按负载在桶之间迁移 （都是 prefill worker ） ， 每个桶有自己的单 batch 算力配额上限
分桶比较生产化， 开源 router 不知道有没有人做， Together 之前探索过
