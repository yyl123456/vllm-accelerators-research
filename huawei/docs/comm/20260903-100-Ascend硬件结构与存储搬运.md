# Ascend 硬件结构与存储搬运

## 文档契约

- **唯一问题/Owner**：Ascend AI Core 的计算/存储/搬运结构如何影响 LLM kernel，而非描述软件 API。
- **依赖输入**：91/92/94 的统一硬件语言。
- **唯一输出**：供 101-105 消费的 Ascend hardware constraints；不声称实测性能。
- **Out of scope**：CANN/TorchNPU（101）、plugin（102-105）、具体SKU未经官方核验的峰值。
- **证据**：华为昇腾官方 CANN/架构资料；设备未在本轮可用。

## 1. 计算分工

Ascend Da Vinci/AI Core 公共编程模型把矩阵/Cube、Vector 与 Scalar/control 视作不同执行资源，并由片上 buffer 与数据搬运单元连接外部 memory。Transformer 的 GEMM/attention matmul 倾向 Cube，norm/activation/softmax/RoPE/quant 等依赖 Vector，地址与循环/同步依赖 Scalar。

`INFERENCE`：只优化 Cube 利用率会把 decode 的 vector/reduction、搬运或 launch 留在关键路径。prefill大矩阵更易铺满Cube；decode小M、长KV更受memory和调度影响。

## 2. 存储层次与 tiling

AI Core 不是直接对全局memory做任意大矩阵。compiler/operator根据shape把输入搬入片上local buffers，分tile执行并写回。tile同时受data dtype、double buffering、accumulator、temporary与多输入约束。动态ragged batch若产生大量tile variants，会增加tiling host work、kernel选择或graph profiles。

KV cache的paged/non-contiguous layout需要block table与gather式访问；若kernel要求连续NZ/private layout，则layout conversion和padding必须纳入bytes与capacity，而不能只报理论HBM。

## 3. 搬运与并发

host↔device、global↔local、device↔device搬运由runtime stream/task与DMA语义协调。batch memcpy、异步copy等API是否存在依赖CANN版本；固定plugin CMake会探测 `aclrtMemcpyBatchAsync` 并在缺失时退回逐次 `aclrtMemcpyAsync`，这是release tuple影响性能路径的源码证据。

## 4. 多芯片

卡内/卡间通信通过HCCL及实际拓扑承载。TP/CP/MoE的集体通信模式不同；逻辑NPU编号不能推导物理link。重复HCCL communicator还会占额外runtime资源，plugin已有handle复用patch/RFC迹象，但是否安全复用取决于rank topology与options。

## 5. 对推理的决策

- prefill：Cube tile/fusion、activation memory与CP；
- decode：weight/KV bandwidth、small-shape kernel与ACLGraph；
- MoE：expert small GEMM、all-to-all/HCCL与placement；
- quant：format是否有native op、scale layout与quality；
- MM：encoder dynamic shapes与独立graph profile。

## 6. 证据边界

- `VENDOR_CLAIM × UNVALIDATED`：150 的 `WEB-ASCEND-02` 支持 AI Core/Cube/Vector/Scalar 与 CANN stack 的存在；不证明固定 plugin 的可达映射。
- `SOURCE_IMPLEMENTED`：plugin源码按SoC/version选择kernels和copy能力。
- `UNKNOWN`：目标SKU sustained bandwidth、tile occupancy、ACLGraph收益、collective p99，必须设备实测。
